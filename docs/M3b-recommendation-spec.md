## M-1. 임베딩 모델 — ✅ `gemini-embedding-2` (768차원)

### 후보 비교 (2026-10 기준)

| 모델 | 가격 (1M 토큰) | 차원 | 비고 |
|---|---|---|---|
| **Google `gemini-embedding-2`** | $0.20 (Batch $0.10) | 128~3072, 768 권장 | Stable. 무료 tier. 입력 8,192토큰 |
| OpenAI `text-embedding-3-small` | $0.02 | 1536 (`dimensions`로 축소) | 2024-01 이후 갱신 없음 |
| OpenAI `text-embedding-3-large` | $0.13 | 3072 (축소 가능) | 한국어 검색 벤치마크(KURE-v1 표)에서 오픈소스 중형 모델보다 낮음 (Recall@10 0.729 vs e5-base 0.735, KURE-v1 0.797) |
| Upstage Embed 2 | $0.02 | 미확인 | 한국어 특화. v1이 2026-12-31 종료 예정 — 모델 교체 주기가 짧다 |
| Voyage 3.5 / Cohere v4 | $0.06 / $0.12 | 1024 / MRL | 이 프로젝트에서 특별한 이점 없음 |

### 결정 근거

- **비용은 기준이 아니다** — 전량 임베딩이 약 5M 토큰이라 가장 비싼 모델로도 약 $1(1회).
  질의는 수십 토큰이라 사실상 0원.
- **한국어 질의 품질 우선 (사용자 결정)** — 작업량은 작지만 질의가 의미상 어렵다. "비 오는 날
  혼자 보기 좋은 잔잔한 영화"처럼 **분위기·감상을 묻는 질의**가 많은데, 줄거리는 이야기를
  설명할 뿐 분위기를 거의 쓰지 않아 모델의 의미 추론력이 품질을 좌우한다.
- **768이 권장 차원**이라 R-4의 39MB 산정이 그대로 맞는다.

### 기각

- **오픈소스 모델 서버 상주** (BGE-M3, multilingual-e5 등) — 질의도 같은 모델로 실시간
  임베딩해야 하므로 결국 서버에 모델이 필요하다. 작은 모델(e5-small, ONNX int8 ≈ 150MB)은
  CPU로도 돌지만 Spring + MySQL이 함께 있는 2GB에서는 빠듯하고 한국어 품질이 떨어진다.
  → **향후 개선 경로로만 남긴다** (아래 `EmbeddingClient` 격리로 교체 비용 최소화).

### 호출 규약 — ⚠️ `task_type`을 쓰지 않는다

공식 문서(Gemini API Embeddings) 확인 결과 **`gemini-embedding-2`는 `task_type` 필드를 받지
않는다.** 질의/문서 구분은 **텍스트 접두어**로 한다.

| 용도 | 형식 |
|---|---|
| 사용자 질의 | `task: search result \| query: {질의}` |
| 영화 문서 | `title: {제목} \| text: {본문}` (제목이 없으면 `title: none`) |

- **`output_dimensionality = 768`** — 축소 차원은 **자동 정규화**된다. 코사인 유사도 = 내적.
- ⚠️ **`embedContent` 한 번에 여러 입력을 넣으면 합쳐진 벡터 1개가 나온다.** 영화별 벡터가
  필요하므로 입력마다 별도 `Content`로 보내거나 Batch API를 쓴다. 가장 실수하기 쉬운 지점.

### 격리 인터페이스

```java
public interface EmbeddingClient {
    float[] embedQuery(String query);                  // 접두어 조립은 구현 내부
    float[] embedDocument(String title, String text);
    String modelName();                                // movie_embedding.model_name 기록용
}
// 구현: GeminiEmbeddingClient. 교체 시 OnnxEmbeddingClient 등 구현 하나 + 전량 재임베딩.
```

- 호출은 **서버에서만**. API 키는 환경변수(`application-secret.yml` 패턴).
- 질의 경로: 타임아웃(예: 3초) → 실패 시 **규칙 기반 추천으로 폴백**, 정규화된 질의 문자열
  캐시(Caffeine). 세부는 API 설계 단계에서 확정.

## E-1. 임베딩 입력 텍스트 — ✅ 확정

### 템플릿

```
title: {표시제목} ({original_title — 표시제목과 다를 때만}) | text: 개봉: {연도}년 · 국가: {국가명들}
장르: {장르1}, {장르2}
상영시간: {구간 라벨} ({runtime}분)
감독: {감독명}
주연: {배우1}, {배우2}, {배우3}
한 줄 소개: {tagline}
키워드: {keyword1}, {keyword2}, …
줄거리: {overview}
```

**값이 없는 줄은 줄째 생략한다** (`라벨: ` 뒤에 빈 값을 남기지 않는다 — 모든 문서에 같은 빈
라벨이 들어가면 잡음이 된다).

### 필드 규칙

| 필드 | 출처 | 규칙 |
|---|---|---|
| 표시제목 | `COALESCE(title_ko, title)` | 화면 표시 규칙과 동일 |
| 원제 | `original_title` | 표시제목과 같으면 생략. "Parasite 같은 영화" 등 원어 질의 대응 |
| 연도 | `release_date` | 연도만. null이면 `개봉:` 항목 생략 |
| 국가 | `movie_country` → `country.name` | `weight` 내림차순 |
| 장르 | `movie_genre` → `genre.name` | |
| 상영시간 | `runtime` | Q-1의 구간 라벨. 보통 구간·null이면 줄 생략 |
| 감독 | `movie_director` → `COALESCE(person.name_ko, person.name)` | 전원 (통상 1~2명) |
| 주연 | `movie_actor` `display_order` 오름차순 상위 3명, 표시명 규칙 동일 | D-1상 0~4가 LEAD이므로 상위 3명은 항상 LEAD. **문제가 생기면 조정** (사용자 결정) |
| 한 줄 소개 | `movie.tagline` (6-11 신설) | 한국어만. null이면 생략. **실측 44%만 보유 — 보조 신호** |
| 키워드 | `movie_keyword` → `keyword.name` (6-11 신설) | 영문. **최대 20개**. 순서는 TMDB 응답 순 |
| 줄거리 | E-2 | |

### 제외

| 필드 | 이유 |
|---|---|
| 평점 · 투표 수 | 숫자는 임베딩에서 의미를 갖지 못한다. **필터·규칙 점수에서 더 잘 쓴다** (사용자 결정) |
| 배역명 · 조연 | 잡음만 늘어남. 배역명은 출처도 불안정(기획노트 인물명 한글화 항목) |
| 상영시간 숫자 단독 | Q-1 참고 — 라벨로 바꿔 넣는다 |

### 규모

영화당 약 250~450토큰 → 전량 약 5M 토큰. 일반 요금 약 $1, Batch API 약 $0.5.

### ⚠️ 인물명 결합 (기획노트 "인물명 한글화" 항목의 경고 대응)

임베딩 입력에 인물명을 넣으므로 **`person.name_ko`가 나중에 채워지면 해당 영화의 입력 텍스트가
바뀐다.** 대응은 E-4의 `source_hash`로 한다 — 갱신 배치가 "현재 조립 결과의 해시 ≠ 저장된
해시"인 영화만 재임베딩하므로, 인물명 보강(카탈로그 보강 C-3 등)이나 `title_ko` 입력 후
**변경분만** 다시 돌리면 된다. 전량 재생성이 필요 없다.

## E-2. 한국어 줄거리 결측 — ✅ A안 (영문 줄거리 폴백)

**실측 (2026-10-22, 6-11 백필 후)** — 12,917편 중 **959편(7.4%)** 이 한국어 줄거리 없음. 이 중 **956편이 영문으로 메워지고**, 둘 다 없는 영화는 **3편(0.02%)** 뿐이다. (10-21 1차 실측은 12,755편 중 979편)

| 우선순위 | 줄거리 값 | `overview_source` |
|---|---|---|
| 1 | `movie.overview` (ko-KR) | `KO` |
| 2 | `movie.overview_en` (6-11 신설) | `EN` |
| 3 | 줄 생략 (메타데이터만) | `NONE` |

- Gemini 2는 다국어 모델이라 **한국어 질의 ↔ 영문 문서** 교차 매칭이 된다.
- `NONE`인 영화도 임베딩한다 — 유사도가 자연히 낮게 나오고 규칙 점수(`vote_count`)가 한 번 더
  거른다. `NONE`은 3편이라 예외 경로로만 다룬다.
- 기각 — B안(메타데이터만: 분위기 질의에 거의 안 걸림), C안(후보 제외: 커버리지 감소).

## E-3. 추가 데이터 수집 경로 — ✅ 동기화 확장

**실행 스펙은 `tmdb-sync-spec.md` 6-11.** 여기는 결정 근거만 남긴다.

| | 기각안: 임베딩 배치가 TMDB 직접 호출 | **채택: 기존 동기화 확장** |
|---|---|---|
| 기존 12,755편 백필 | 12,755회 | **동일** 12,755회 (기존 `resync` 경로) |
| 신규 영화 | 편당 +1회 | **+0회** (`append_to_response` 추가) |
| 임베딩 배치의 외부 의존 | TMDB + Gemini | **Gemini만** |
| DB 변경 | 없음 | `movie` 컬럼 2 + 테이블 2 |
| 데이터 재사용 | 임베딩 전용 | 화면(태그라인 등)에서도 사용 가능 |

- **호출량은 결정 기준이 아니었다** — 두 안 모두 백필이 같다.
- **결정 근거는 책임 분리** — 동기화 = TMDB → DB, 임베딩 배치 = DB → 텍스트 → Gemini.
  기각안은 임베딩 배치에 외부 API 두 개와 실패 지점 두 곳을 준다.

## Q-1. 질의 조건 추출 — 상영시간 ✅ 확정

**문제** — "짧은 영화", "금방 볼 수 있는" 같은 질의는 숏폼 시대에 수요가 있으나(사용자 판단)
**임베딩은 "짧은"과 `88분`을 연결하지 못한다.** 오히려 줄거리의 "짧은 인생", "짧은 여름"이 걸린다.

### ① 문서 쪽 — 구간 라벨 (E-1 템플릿의 `상영시간:` 줄)

| `runtime` | 출력 |
|---|---|
| ≤ 95 | `상영시간: 짧은 편 (88분)` |
| 96 ~ 139 | 줄 생략 (모든 문서에 같은 라벨이 들어가면 잡음) |
| ≥ 140 | `상영시간: 긴 편 (152분)` |
| null | 줄 생략 |

### ② 질의 쪽 — `QueryConstraintExtractor` (핵심)

사전·정규식 기반으로 질의에서 런타임 조건을 뽑아 **규칙 점수 단계**에 반영한다.

| 질의 예 | 추출 | 적용 |
|---|---|---|
| "90분 이내", "1시간 반 안에" | `runtime ≤ 90` | **하드 필터** — 명시 조건 |
| "짧은", "가볍게 금방" | `runtime ≤ 100` 선호 | **가산점** — 모호하므로 결과를 0건으로 만들지 않는다 |
| "긴", "대작", "3시간짜리" | `runtime ≥ 140` 선호 | 가산점 |

- 하드 필터에서 `runtime` null인 영화는 제외한다.
- 추출된 조건은 **추천 이유**로 노출 가능("90분 이하 영화 위주로 골랐어요").
- 가산점 크기는 점수 공식 단계에서 확정.
- **범위는 상영시간만.** 연도("90년대")·국가("홍콩 영화")는 같은 구조로 패턴만 추가하면 되나
  이번 범위 밖.
- **LLM 질의 파싱은 기각(향후 개선)** — 유연하지만 질의마다 LLM 호출이 추가돼 지연·비용 증가.

## Q-2. 질의 조건 추출 확장 — 국가 · 개봉 시기 · 부정 표현 ✅ 확정 (2026-10-26)

> Q-1(상영시간)을 확장한다. 계기 — *"90년대 한국 영화"* 에 외국 영화가 섞이는 것은 이상하다(사용자 지적).
> 임베딩은 문장 전체를 벡터 하나로 압축해 **여러 조건이 희석되고, 부정을 처리하지 못한다**("공포 말고"가 오히려 공포 쪽으로 당긴다).
> **사용자가 명시한 조건은 규칙이 지킨다** — "90분 이내"를 하드 필터로 둔 것과 같은 논리.

### Q-2-1. 국가

| 표현 | 처리 |
|---|---|
| "한국 영화"·"한국영화"·"국내 영화", "일본 영화", "할리우드 영화"(→ US) 등 | **하드 필터 `COUNTRY`** |
| "외국 영화"·"해외 영화" | **하드 필터 `EXCLUDE_COUNTRY`(KR)** |
| "일본 영화 **느낌**", "홍콩 영화 **스타일**", "**~풍**", "**~감성**" | **추출하지 않는다** — 제작국이 아니라 분위기. 임베딩에 맡긴다 |

- 판정은 **대표국**(`movie_country.weight` 최댓값, D-3) — Pop의 한국 그룹 판정과 같다.
- 사전(시작): 한국·국내 / 일본 / 미국·할리우드 / 홍콩 / 중국 / 대만 / 프랑스 / 영국 / 인도 / 스페인 / 독일 / 이탈리아 → ISO 코드.

### Q-2-2. 개봉 시기 — `RELEASE_PERIOD`

| 표현 | 범위 (`Clock` KST 오늘 기준) | 칩 |
|---|---|---|
| "90년대"·"2000년대 영화" (50~90년대, 2000·2010·2020년대) | 해당 10년 | "1990년대" |
| "최근 영화"·"요즘 영화"·"최근 개봉작" | **오늘 − 5년** 이후 (사용자 결정) | "최근 5년" |
| "옛날 영화"·"오래된 영화"·"고전 영화" | **오늘 − 20년** 이전 (사용자 결정) | "20년 이전" |

- 5·20년은 프로퍼티(`query.recent-years`·`query.old-years`). "고전"은 "옛날"과 같은 범위로 묶었다 — 어색하면 평가 세트로 분리.
- **영화를 꾸밀 때만 추출** — "최근**에 본** 것 같은", "최근 **들어** 우울해서"는 사용자의 시점이라 제외. "감성·느낌·스타일·풍" 규칙도 적용.
- **둘 이상이면 더 구체적인 것 하나** — 연대 > 최근/옛날 (교집합 0건 방지).
- `release_date` null은 시기 필터에서 제외.

### Q-2-3. 부정 표현 — "긍정형으로 추출 후 역" (사용자 제안)

부정 대상이 **분류인지 분위기인지**로 나뉜다.

**① 분류(장르·국가) — 제안 그대로: 긍정형 추출 → 제외 필터**

```
"공포 말고 스릴러"  → "공포" 추출 → EXCLUDE_GENRE(공포) 하드 필터
"한국 영화 말고"    → "한국" 추출 → EXCLUDE_COUNTRY(KR)
```

DB에 명확한 값이 있어 "역"이 정확히 정의된다. 장르 사전(공포·호러 / 로맨스 / 액션 / 코미디 / 애니·애니메이션 / 다큐 / SF …)에 없는 명사는 ②로 간다.

**② 분위기 — 긍정형 추출 → "역"이 아니라 감점**

⚠️ "잔인한"과 **가장 먼** 영화를 내면 "순한 영화"가 아니라 **"잔인함과 무관한 영화"**(자연 다큐·음악 영화 등)가 나오고
질의 맥락(스릴러)이 사라진다. 그래서 **부정 개념과 가까운 후보를 뒤로 민다**(네거티브 프롬프트와 같은 원리).

```
"잔인하지 않은 스릴러"
  ① 부정 구간 분리    본 질의 = "스릴러",  부정 개념 = "잔인하다"
  ② 본 질의로 후보 200편 (맥락 유지)
  ③ S = 0.6·sim(본 질의) + 0.25T + 0.15Q + 런타임·조건 가산 − γ·sim(부정 개념)
```

- **부정 구간을 본 질의에서 지운다 — 이것이 핵심.** 남겨 두면 "잔인"이 벡터를 잔인한 쪽으로 당긴다.
- `sim(부정 개념)`도 후보 안 min-max로 0~1. **γ = 0.3** (프로퍼티, 효과가 없으면 0으로 끈다).
- **긍정형 변환 규칙 — 어간 + "다"** — 관형형 복원은 불규칙 활용(무겁다→무거운, 슬프다→슬픈) 때문에 어렵지만
  기본형은 항상 맞다.

| 패턴 | 예 | 부정 개념 |
|---|---|---|
| 어간 + **지 않은/않는** | 잔인하지 않은 · 무겁지 않은 · 슬프지 않은 | 잔인하다 · 무겁다 · 슬프다 |
| 명사 + **말고/빼고/제외/아닌** | 공포 말고 | 장르 사전이면 ①, 아니면 ② |
| 명사구 + **없는** | 잔인한 장면 없는 | "잔인한 장면" → ② |

| 항목 | 처리 |
|---|---|
| 추가 호출 | 부정 개념당 임베딩 1회. 질의 임베딩 캐시 공유("잔인하다"·"무섭다"는 금방 캐시에 걸린다). **실제 호출이라 호출 제한에 센다** |
| 본 질의가 비면 | "잔인하지 않은 영화" → 본 질의 sim = 0, **T·Q·Pop + 감점**만. 결과는 "잔인하지 않은 쪽의 내 취향" |
| 개수 | **최대 2개** — 그 이상은 호출이 늘고 감점이 상쇄된다 |
| 칩 | ① "공포 제외" / ② "잔인한 영화는 뒤로 미뤘어요" |

### Q-2-4. ⚠️ 하드 필터는 후보를 뽑기 **전에** 적용한다 (S-1-4 개정)

```
기존: 전체 → 유사도 상위 200 → 하드 필터 → 남은 것
변경: 전체 → 하드 필터(국가·시기·제외 장르·런타임·시청·하한) → 그 안에서 유사도 상위 200
```

- 한국 영화는 카탈로그의 12%, "90년대 한국 영화"는 훨씬 적다 — 기존 순서면 상위 200편에 몇 편 없거나 **없어서**,
  DB에 있는데도 "결과 없음"이 된다. **런타임 필터도 같은 문제였다.**
- **추가 비용 0** — 어차피 전수 스캔이라 스캔하며 조건을 검사한다. 판정 값(국가·개봉일·런타임·장르)은 `MovieFeatureIndex`에 있다.
  `MovieVectorIndex.search(queryVector, k, IntPredicate allowed)` — 인덱스 위치 기준 판정 함수.
- 정말 0건이면 DB에 없는 것이다 → `EmptyState` + 조건 칩.

### Q-2-5. 범위 밖 (평가 세트로 판단)

- **유사작 질의** — "○○ 같은 영화"를 감지해 그 영화의 벡터를 질의로 쓰는 안. 비용이 작아 우선순위가 높다.
- **LLM 질의 해석** — 생성 모델로 질의를 구조화. ②·유사작으로 부족할 때만.

## E-4. `movie_embedding` · 생성/갱신 배치 · 메모리 인덱스 — ✅ 확정 (2026-10-22)

### E-4-1. 테이블

```sql
CREATE TABLE movie_embedding (
  id              BIGINT          NOT NULL AUTO_INCREMENT,
  movie_id        BIGINT          NOT NULL,
  model_name      VARCHAR(50)     NOT NULL,   -- 'gemini-embedding-2'
  dimensions      SMALLINT        NOT NULL,   -- 768
  embedding       VARBINARY(3072) NOT NULL,   -- float32 × 768, little-endian
  source_text     VARCHAR(4000)   NOT NULL,   -- 조립된 입력 텍스트
  source_hash     CHAR(64)        NOT NULL,   -- SHA-256(model_name + source_text)
  overview_source VARCHAR(10)     NOT NULL,   -- KO / EN / NONE (EnumType.STRING)
  created_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at      DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_movie_embedding_movie (movie_id),
  CONSTRAINT fk_movie_embedding_movie FOREIGN KEY (movie_id) REFERENCES movie (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

| 결정 | 이유 |
|---|---|
| **영화당 1행** (모델별 행 아님) | 모델 교체는 드물고 전량 재임베딩이 $1 미만 — 덮어쓴다 |
| `VARBINARY(3072)` (BLOB 아님) | `@Column(length = 3072)` 한 줄로 `ddl-auto=validate` 통과 (D-4가 TEXT 대신 VARCHAR를 고른 이유와 같다). 차원 변경 시 마이그레이션 필요 — 의도된 변경이다 |
| 바이트 순서 little-endian 고정 | 변환은 **`VectorCodec` 한 곳**(`ByteBuffer.order(LITTLE_ENDIAN)`). 쓰기·읽기가 어긋나면 **예외 없이 엉뚱한 결과**가 나는 유형 |
| `source_text` `VARCHAR(4000)` | 필드 상한 합 약 3,000자. TEXT 컬럼 없는 관례 유지 |
| 해시에 `model_name` 포함 | 모델 교체 = 전 행 해시 불일치 = 별도 로직 없이 전량 재임베딩 |
| 영화 FK CASCADE | 영화가 없으면 벡터도 의미 없다 |

- 엔티티 `MovieEmbedding` — `@ManyToOne(LAZY)`가 아니라 **`movieId` 단순 컬럼**도 고려 가능하나,
  프로젝트 표준(단방향 `@ManyToOne(LAZY)`, cascade 없음)을 따른다. 갱신은 정적 팩토리 + `replace(...)` 메서드.

### E-4-2. 생성 위치 — **서버** (⚠️ R-4 일부 수정)

R-4의 *"영화 벡터는 개발 PC에서 배치 생성 후 적재"* 는 **로컬 모델을 쓸 수도 있다는 전제**였다.
외부 API로 확정되며 전제가 사라졌다.

| | 개발 PC | **서버 (채택)** |
|---|---|---|
| 입력 | 영화 원본이 운영 DB(D-5) — 로컬과 어긋나거나 SSH 터널 필요 | 운영 DB 직접 |
| 반영 | 덤프 → 운영 적재 | 즉시 저장 |
| 신규 영화 | 매번 수동 | 스케줄 자동 |
| 서버 부담 | 없음 | HTTP 호출뿐, 100편 단위 처리 — 미미 |

### E-4-3. 배치 흐름

```
EmbeddingSyncService (트랜잭션 없음)
 └ id 커서, 100편 단위
    1. 영화 + 연관(장르·국가·감독·주연·키워드) IN절 벌크 조회 — 프로젝트 표준
    2. EmbeddingTextBuilder.build(...) → source_text, overview_source   ← 순수 함수
    3. SHA-256 계산 → 기존 movie_embedding IN 조회 → 행 없음 or 해시 불일치만 대상
    4. 대상만 Gemini batchEmbedContents 1회 요청
    5. MovieEmbeddingPersister(@Transactional) upsert
 └ 종료 후 MovieVectorIndex.reload()
```

- **트랜잭션 분리** — 6-4 원칙(HTTP는 트랜잭션 밖, 저장만 별도 빈). 같은 클래스 분리는 자기호출이라
  `@Transactional`이 무시된다.
- **`batchEmbedContents`** — 요청별 벡터가 요청 순서대로 온다. M-1의 *"`embedContent` 다중 입력은 합쳐진다"*
  함정을 피하는 경로. ⚠️ 공식 API 레퍼런스 예시가 `embedding-001`뿐이라 **구현 시 `gemini-embedding-2`로
  2건 요청 → 벡터 2개 응답을 먼저 확인**한다.
- **비동기 Batch API(50% 할인) 기각** — 전량이 $1이라 할인 의미가 없고 작업 제출·폴링 구조만 생긴다.
- **결정성 (⚠️ 요금 사고 방지)** — `EmbeddingTextBuilder`의 모든 목록에 **정렬 기준을 명시**한다
  (국가 `weight DESC, id`, 장르 `id`, 감독 `id`, 주연 `display_order`, 키워드 `movie_keyword.id`).
  순서가 흔들리면 매일 해시가 바뀌어 **매일 전량 재임베딩**된다. *"같은 입력 → 같은 텍스트"* 를 단위 테스트로 고정.
- **이상 감지** — 1회 실행의 `embedded`가 500을 넘으면 `WARN` (첫 적재·모델 교체 같은 수동 실행은 예외로 본다).
- 429 → 백오프 후 `break`, **`lastProcessedId`는 처리 못 한 영화 앞에서 멈춘다**(resync 규칙). 개별 실패는 skip + 집계.
- 결과 DTO `EmbeddingSyncResult(embedded, unchanged, failed, stoppedByRateLimit, lastProcessedId)`.
- 예상 소요 — 12,917편 ≈ 130회 묶음 요청. **⚠️ 무료 tier는 분당 100 요청이고 배치 문서 1건이 요청 1건으로 계산된다**(2026-10-26 실측,
  `embed_content_free_tier_requests, limit: 100`) — 100편 묶음 하나가 1분 한도를 다 쓰므로 **전량 약 2시간**이다. 유료 tier는 한도가 훨씬 커서 수 분(전환 시 실측).
  429 응답에는 `Retry-After` 헤더가 없고 **본문에 `Please retry in 28.7s`** 로만 대기 시간이 온다 — 클라이언트가 이 숫자만 꺼내 쓴다.
  서버 안내 대기가 `max-wait`(90초)를 넘으면(일일 한도 소진 등) 잠들지 않고 중단해 `lastProcessedId`를 돌려준다.
  **⚠️ 무료 tier는 일일 한도도 있다 — 1,000 요청/일**(`limit: 1000 … requests per day`, 대기 안내 `1h7m…`). 1,000편 적재 직후 막혔고, 전량(12,755편)은 무료 tier로 **약 13일**이다.
  **전량 적재는 유료 tier 전환 후에 한다**(운영 첫 적재도 마찬가지). 대기 안내는 `28.7s`뿐 아니라 `1h7m33s` 형식도 온다.

| 안 | 판정 |
|---|---|
| ⓐ 동기화 직후 즉시 임베딩 | ❌ 동기화가 Gemini에 의존 (E-3의 책임 분리 붕괴) |

| **ⓒ 전량 해시 비교 (채택)** | ✅ 무엇이 바뀌든 텍스트가 바뀌면 잡힌다. 비용은 DB 읽기뿐 |

  ⚠️ **무료 tier 적재 기간은 17:10 · 1회 800편** — OP-1-2.
- **관리자 수동 실행** — `POST /api/admin/embeddings/sync`. **필요한 순간에만** 쓴다:
  첫 적재 · 시연 전 즉시 반영 · 인물명 일괄 보강 직후 · 모델/템플릿 변경 직후 · 429/장애 중단 후 재개.

- **감수** — 온디맨드로 새로 들어온 영화는 **다음 날부터** 자연어 추천에 나온다.

### E-4-5. 메모리 인덱스 `MovieVectorIndex`

```
long[]  movieIds   // n
float[] vectors    // n × 768 연속 배열
```

- **적재** — `ApplicationReadyEvent`에서 전량 로드. **현재 `EmbeddingClient.modelName()`·768과 일치하는 행만** —
  모델 교체 중 섞인 옛 벡터는 무시된다.
- **교체** — 배치 종료 후 새 인덱스를 만들어 **`AtomicReference`로 한 번에 교체**. 검색 중인 요청은 반쯤
  만든 인덱스를 보지 않는다.
- **메모리** — 평소 ≈ 40MB, 교체 순간 두 벌 ≈ **80MB** (힙 640MB). `deploy-spec.md` 메모리 예산에 반영.
- **검색** — 전수 내적(정규화 벡터라 = 코사인) + 최소 힙 top-K. 약 1천만 곱셈·덧셈, 수 ms.
- 삭제된 영화가 인덱스에 남아 있을 수 있다 — 결과 조립 단계에서 IN 조회에 없는 id는 버린다.
- **인덱스가 비면**(첫 배포 직후 등) 자연어 추천은 규칙 기반으로 폴백.

### E-4-6. Gemini 요금 tier

## S-1. 점수 공식 — ✅ 확정 (2026-10-26)

### 전체 구조

```
[내 취향 추천]  전체 영화 ─ 제외 규칙 ─▶ S = T·Q·Pop 결합 ─▶ 다양성 보정 ─▶ 상위 100 확정 → 20편씩 페이징
[자연어로 찾기] 질의 ─▶ 임베딩 상위 K=200 ─ 하드 필터 ─▶ S = sim·T·Q·런타임 결합 ─▶ 상위 100 → 페이징
```

**두 기능이 취향 점수 T와 품질 점수 Q를 공유**하고, 자연어에만 유사도가, 취향 추천에만 인지도 Pop(S-1-3-B)이 붙는다.
**모든 구성 요소를 0~1로 정규화**한다 — 가중치가 곧 비중이 되어 해석·튜닝이 독립적이다.

### S-1-1. 사용자 선호 프로필 — ⚠️ 네 축 모두 평균 중심 합 (M3-a 점수를 그대로 쓰지 않는다)

M3-a 11-4는 *"인물은 평균형, 장르·국가는 합계형이라 스케일이 다르다 — M3-b에서 정규화"* 로 넘겼다.
문제는 스케일만이 아니다. **합계형 장르 점수는 "많이 봤지만 낮게 평가한" 장르를 선호로 본다** —
공포를 많이 보며 늘 4점을 주는 사용자에게 공포를 계속 추천하게 된다. 리포트에선 맞는 말("많이 본 장르"),
추천에선 틀린 결과다.

```
축 점수(x) = max(0, Σ (별점 − m) × w)       m = 사용자 누적 평균 별점 (M3-a statistics.averageRating)
정규화     = 축 점수(x) / 그 축의 최댓값      → 0~1  (최댓값이 0이면 축 전체 0)
```

| 축 | `w` | 비고 |
|---|---|---|
| 장르 `G` | `movie_genre.weight` (1/N) | |
| 국가 `C` | `movie_country.weight` | 영화당 합 = 1 (`(N+1)/(N²+1) + (N−1)·N/(N²+1)`) |
| 감독 `D` | 1/N (공동 연출 분배, RA-4) | |
| 배우 `A` | `RoleTier.weight`, **애니메이션 제외**, `EXTRA` 제외 | M3-a 11-2 규칙 그대로 |

- 집계 대상은 M3-a RA-1과 같다 — **대표 기록 + `rating IS NOT NULL`**.
- **리포트는 바꾸지 않는다.** M3-b 전용 프로필 쿼리를 둔다. 조인·가중치 형태는 M3-a와 같아 R-2의
  *"M3-a 재사용"* 취지는 유지되고 점수식만 다르다. 이로써 11-4가 감수한 스케일 불일치가 M3-b에서 해소된다.
- **평균 이하로 본 축은 0** — 감점까지 하지 않는다. 감점은 별점을 짜게 주는 사용자의 결과를 크게 흔든다.
- **최댓값 정규화** — 기록 10편이든 500편이든 *"내 안의 1등 = 1.0"* 이라 같은 가중치가 통한다.
- 모든 별점이 같으면(기록 1건 포함) 전 축이 0 → 콜드 스타트와 같은 동작 (R-3에서 다룸).
- **찜은 W-1에서 이 프로필(장르·국가·감독)에 결합한다.**

### S-1-2. 영화의 취향 점수 T (0~1)

```
T = wG × Σ(movie_genre.weight × G[장르])
  + wC × Σ(movie_country.weight × C[국가])
  + wP × P

P = max( D[감독들], A[주연 — display_order 0~4, 애니메이션이면 배우 항 제외] )
```

- 장르·국가 항은 영화 쪽 가중치 합이 1이라 **자동으로 0~1**(가중 평균).
- **인물 항은 합이 아니라 `max`** — 합이면 좋아하는 배우가 여럿 나오는 앙상블·시리즈물이 항상 이긴다
  (M3-a 11-1의 시리즈물 효과가 추천에서 재발). `max`는 그대로 **추천 이유**가 된다.
- 애니메이션 영화는 배우 항을 보지 않는다(11-2와 정의 일치). 감독 항은 본다.

### S-1-3. 품질 점수 Q (0~1) — 투표 수 보정 평균

```
Q = (v × R + k × M) / (v + k) / 10        v = vote_count, R = vote_average
M = 6.63   (실측 2026-10-25, vote_count > 0 평균)
k = 707    (실측 2026-10-25, vote_count 중앙값)
```

- IMDb Top 250 가중 평점과 같은 원리. 6-9가 `vote_count`를 함께 저장한 이유("3명 10.0" vs "22,061명 8.4")를 쓴다.
- `vote_count` null/0 → `Q = M / 10`.
- ⚠️ **k = 707은 큰 편** — 표가 적은 한국 영화가 평균 쪽으로 당겨진다(「길복순」 184표 7.5 → 약 6.8).
  Q 비중이 0.20/0.15라 순위를 뒤집진 않는다고 보고 시작하되, **평가 세트에서 한국 영화가 과하게 밀리면 k를 낮춘다.**
- M·k는 상수가 아니라 프로퍼티. 카탈로그가 크게 바뀌면 같은 SQL로 재실측한다.

### S-1-3-B. 인지도 — 투표 수 하한 + Pop 항 (2026-10-26 추가)

**문제** — Q의 투표 수 보정은 표가 적은 영화를 평균(6.63) 쪽으로 **당길 뿐 아래로 내리지 않는다.**
7.0점·10표 무명작의 Q(0.664)가 6.0점·5,000표 유명작(0.608)을 이긴다. Q는 *"3명 10점"* 을 막는 장치이지
인지도 장치가 아니다. → 추천 결과가 무명작으로만 채워질 수 있다.

**실측 (2026-10-26, 대표국 = `movie_country.weight` 최댓값)**

| 대표국 | 전체 | < 30표 | < 100표 | < 300표 |
|---|---|---|---|---|
| 한국 | 1,556 | **724 (46.5%)** | 1,210 | 1,443 |
| 그 외 | 11,168 | 22 | 657 (5.9%) | 2,244 |
| 국가 없음 | 31 | 10 | 19 | 24 |

- 30표 미만 한국 영화 중 **716편은 박스오피스 기록도 없다** — "KR 30표 OR 박스오피스" 구제안은 효과가 없었다.
- v₉₉ — 전체 **16,674** / 한국 **1,598**.

#### ① 투표 수 하한 (하드 필터, 취향·자연어 공통)

| 대상 | 하한 | 근거 |
|---|---|---|
| **한국** | **없음** | **카탈로그 자체가 하한이다** — 6-10 한국 영화 시드가 `lang=ko · minVotes=10 · vote_count.desc` 상위 3,000이었고 실제 적재는 1,556편 → *TMDB 10표 이상 한국어 영화를 사실상 전량* 가져왔다. 나머지는 온디맨드(누군가 기록한 영화)·박스오피스 경로라 관심이 검증된 영화다 (사용자 판단) |
| **그 외 · 국가 없음** | **`vote_count ≥ 50`** | 정보가 거의 없는 영화만 거른다. 무명작을 밀어내는 주 장치는 하한이 아니라 ②다. **표가 적어도 좋은 영화를 최대한 살린다** (사용자 결정, 100 → 50) |

- `vote_count` null은 하한 대상(그 외)에서 제외된다.

#### ② Pop 항 (취향 추천에만)

```
Pop = min(1, log(1 + vote_count) / log(1 + v₉₉[그룹]))     그룹: 한국 1,598 / 그 외 16,674
      vote_count null → 0
```

- **log** — 표 수는 10~3만으로 폭이 커서 그대로 쓰면 블록버스터만 나온다. 100↔1,000 차이는 크게, 1만↔3만은 작게.
- **그룹별 v₉₉** — TMDB가 한국 영화를 구조적으로 덜 다룬다(위 실측). 전체 기준이면 한국 영화 50표 = 0.41,
  해외 3,000표 = 0.82로 **한국 영화가 일관되게 밀린다.** 그룹 기준이면 한국 50표 = 0.53, 500표 = 0.84 —
  *"한국 영화 중에서 얼마나 알려졌나"* 를 잰다. 시드 프로필이 한국 기준을 따로 둔 것과 같은 이유.
- **자연어에는 넣지 않는다** — 질의 의도가 우선이고 ① 하한으로 충분하다.
- **Q와 합치지 않는다** — "평이 좋은가"와 "알려져 있는가"는 다른 질문이고, 디버그에서 따로 보여야 조정할 수 있다.
- v₉₉는 프로퍼티. 카탈로그가 크게 바뀌면 같은 SQL로 재실측.

**기각 — KOFIC 누적 관객 수 보완 (`max(Pop_tmdb, Pop_kofic)`)** — 박스오피스 수집 이후 개봉작에만 값이 있어
적용 대상이 너무 적다(30표 미만 한국 영화 724편 중 박스오피스 기록이 있는 것은 8편). 같은 해 흥행작이라도 수집
시점에 따라 보정 여부가 갈려 **일관성이 깨지고**, 한국 영화 불리함의 주 원인은 그룹별 v₉₉로 이미 해소된다 (사용자 결정).
**감수** — 최근 개봉작은 표가 쌓일 때까지 Pop이 낮다(가중치 0.15라 영향 제한적). KOBIS 영화 상세로 과거 관객 수를
일괄 보강하면 재검토할 수 있다(향후 후보, 기획노트 인물명 한글화 ⓒ와 같은 경로).

### S-1-4. 최종 점수

**내 취향 추천**

```
S = 0.65 × T + 0.20 × Q + 0.15 × Pop        (10-26 개정: 0.75T + 0.25Q → Pop 추가)
```

- 제외 — 시청 기록이 있는 영화(전 회차 기준, 대표 여부 무관) · `release_date > today` · `release_date IS NULL` ·
  **찜한 영화**(W-1) · **투표 수 하한 미달**(S-1-3-B ①).
- **다양성** — 결과 목록 전체에서 **같은 감독 최대 2편**. 넘치면 다음 순위로 채운다. 공동 연출은 감독 중
  하나라도 상한에 걸리면 제외.

**자연어로 찾기**

```
S = 0.60 × sim + 0.25 × T + 0.15 × Q + 0.10 × [Q-1 런타임 선호 조건 충족] − γ × sim(부정 개념)   (γ 항은 Q-2-3 ②)
```

| 단계 | 규칙 |
|---|---|
| 하드 필터 (**먼저**, Q-2-4) | Q-1 명시 런타임 · Q-2 국가/제외 국가/개봉 시기/제외 장르 · 시청 기록 있는 영화 · 투표 수 하한(S-1-3-B ①). 찜한 영화는 제외하지 않고 `wished = true` (W-1) |
| 후보 | 필터를 통과한 영화 안에서 임베딩 코사인 상위 **K = 200 (고정)** |
| `sim` 정규화 | **후보 집합 안에서 min-max** → 0~1. 코사인 절대 수준은 모델마다 달라 상대화해야 가중치 의미가 유지된다. 후보가 1편이거나 max = min이면 `sim = 1` |
| 런타임 가산점 | Q-1의 모호한 조건("짧은"·"긴")을 만족하면 +0.10. 조건이 없으면 항 자체가 0 |

- 유사도가 가장 크다 — **질의 의도가 결과를 지배**하고, T·Q는 관련 후보 사이의 순서만 바꾼다.
- 자연어는 다양성 상한을 적용하지 않는다 — 사용자가 *"봉준호 영화"* 를 물으면 같은 감독이 정답이다.
- ⚠️ **K는 페이지마다 바꾸지 않는다** — min-max가 후보 집합에 의존하므로 K가 바뀌면 점수 자체가 바뀐다.

**콜드 스타트** — T = 0. 자연어는 sim + Q로 정상 동작, 취향 추천은 *"품질 순"* 이 된다. 다듬는 것은 R-3.

### S-1-5. 추천 이유

**최종 점수에 가장 크게 기여한 항**(가중치 곱한 값 기준)을 문구로 바꾼다.

| 최대 기여 항 | 문구 예 |
|---|---|
| 인물 `P` | "좋아하는 감독 봉준호의 작품" / "좋아하는 배우 송강호 출연" — `max`를 낸 인물 |
| 장르 | "자주 좋게 본 스릴러" — 기여가 가장 큰 장르 |
| 국가 | "좋아하는 한국 영화" |
| 품질 `Q` | "평이 좋은 작품" |
| 인지도 `Pop` | "많은 사람이 본 작품" |
| 찜 관심 (W-1) | "찜 목록에 많은 공포 장르" / "찜 목록에 봉준호 감독 작품이 많아요" |
| 자연어 런타임 조건 | "90분 이하 영화 위주로 골랐어요" — 결과 목록 상단에 1회 |

자연어에서 `sim`이 최대 기여 항이면 영화별 이유를 달지 않는다(질의 자체가 이유). 문구·필드 형태는 API 단계에서 확정.

### S-1-6. 구현 구조

**`MovieFeatureIndex` (메모리)** — 취향 추천은 요청마다 **전 영화**를 채점한다. 매번 1.3만 편 조인 대신
영화별 특징을 메모리에 둔다.

```
영화별: 장르(id, weight)[] · 국가(id, weight)[] · 감독 id[] · 주연 id[](display_order 0~4)
        isAnimation · runtime · releaseDate · voteAverage · voteCount
        isKorean(대표국)          + 카탈로그 장르·국가 비율 p_cat (W-1)
```

- 수 MB, 전수 채점 수 ms. **기동 시 + 매일 06:00 배치 직후** `MovieVectorIndex`와 함께 재생성·`AtomicReference` 교체.
- 요청마다 DB에서 읽는 것은 **사용자 프로필(집계 4쿼리)과 시청 기록 movie_id 목록**뿐.

**페이징 — 상위 100편 확정 후 캐시에서 자르기**

| 항목 | 값 |
|---|---|
| 총 결과 상한 | **100편** (20편 × 5페이지) |
| 1페이지 | 순위 100편 확정(다양성 보정 포함) → 캐시 |
| 2페이지~ | 캐시에서 슬라이스, 계산 없음 |
| 캐시 키 | 취향: `userId` / 자연어: `userId + 정규화된 질의` |
| 캐시 수명 | 10분 (Caffeine). 만료 시 재계산 — 채점이 결정적이라 데이터가 같으면 같은 순서 |
| 메모리 | 항목당 수 KB |

- **페이지마다 재계산하지 않는 이유** — 비용은 거의 0이지만(외부 비용은 질의 임베딩뿐이고 질의 캐시가 막는다)
  ① 보는 도중 시청 기록이 추가되면 순위가 밀려 **중복·누락**이 생기고 ② 다양성 상한이 페이지 경계에서 틀어진다.
- **상한 100의 이유** — 100위 밖은 *"취향이라서"* 의미가 옅어져 사실상 평점 순 목록이 된다. 자연어는 K=200
  고정이라 필터 후에도 100편을 채운다.
- 페이징 형식(`page`/`size`·`hasNext`)은 API 단계에서 `controller-layer-spec.md` 5-0 규약에 맞춘다.

### S-1-7. 가중치 관리 · 튜닝

**모든 가중치·상수는 프로퍼티** — 시드 프로필과 같은 원칙(실행 결과를 보고 조정할 값).

```yaml
cinemory:
  recommend:
    taste:   { genre: 0.5, country: 0.2, person: 0.3 }   # T 내부
    for-you: { taste: 0.65, quality: 0.20, popularity: 0.15 }
    query:   { similarity: 0.60, taste: 0.25, quality: 0.15, runtime-bonus: 0.10, candidate-size: 200,
               negative-penalty: 0.3, max-negatives: 2, recent-years: 5, old-years: 20 }
    quality: { mean: 6.63, min-votes: 707 }               # M, k
    popularity: { v99-korean: 1598, v99-other: 16674 }
    min-vote-count: { korean: 0, other: 50 }
    wish: { lambda: 0.3, smoothing: 5, min-director-wishes: 2 }
    max-per-director: 2
    max-results: 100
    page-size: 20
    cache-ttl: 10m
```

**수정 비용**

| 바꾸는 것 | 방법 | 비용 |
|---|---|---|
| 위 값 전부 | yml 수정 → 재기동 | 몇 분 (재기동 20~30초 중단). 재임베딩·DB·앱 업데이트 불필요 |
| 공식 구조(`max`→합, 축 추가 등) | 코드 → PR → CI 배포 | 몇 시간, 데이터 그대로 |
| 임베딩 입력 텍스트(E-1·Q-1 ①) | 코드 → 배포 → 수동 재임베딩 | 배포 + 수 분, 약 $1 |

**가중치는 임베딩과 독립이다** — 벡터는 "영화가 무엇인가"만, 가중치는 "결과를 어떻게 섞을까"만 담는다.

**튜닝 장치 2종**

1. **점수 분해 디버그 엔드포인트 (관리자 전용)**
   ```
   GET /api/admin/recommendations/debug?userId={id}[&query={q}]
   → 영화별 sim · 장르항 · 국가항 · 인물항(P와 그 인물) · T · Q · Pop · 런타임 가산 · S · 제외 사유
     + 사용자 프로필의 축별 평가 기여 / 찜 관심 기여 (W-1)
   ```
   감이 아니라 숫자로 조정한다. 관리자 감사 로그(admin-spec) 대상 여부는 API 단계에서 정한다.
2. **고정 평가 세트** — 한국어 자연어 질의 20개 + 테스트 계정 2~3개. 가중치를 바꿀 때마다 같은 세트의 상위 10편을
   이전 결과와 비교한다(한 질의를 고치다 다른 질의가 나빠지는 것을 잡는다). 결과는 주간 보고서 자료로도 쓴다.
   세트 자체(질의 목록·기대 결과 메모)는 `docs/` 아래 별도 파일로 둔다 — 작성은 구현 직후.
   **유형별 구성 (2026-10-26)** — 분위기 단일 6 · 런타임 포함 3 · 복합 조건(국가·시기) 4 · 부정 표현 3 · 유사작("○○ 같은") 2 ·
   감독·배우 이름 2. 판단 기준 — 부정 질의에서 γ 효과 확인(없으면 0) / 유사작이 약하면 Q-2-5 유사작 질의 추가 /
   복합·부정이 ②로도 부족할 때만 LLM 질의 해석 검토.

**기각 — 런타임 가중치 변경(DB 설정 테이블 + 관리자 화면)** — 튜닝은 몰아서 하는 작업이라 재기동 30초가
문제가 아니고, 설정 테이블·화면·캐시 무효화 비용만 생긴다. 튜닝이 잦아지면 재검토.

## W-1. 찜(위시)을 선호 신호로 — ✅ 확정 (2026-10-26)

> 기획노트 R-1이 이관한 *"`wish_movie`를 선호 신호로 볼지"* 의 결론이다. **반영한다.**

### 원칙 — 찜은 "평가"가 아니라 "관심 속성"이다

| | 시청 기록 + 별점 | 찜 |
|---|---|---|
| 의미 | 보고 나서 평가한 결과 | 보고 싶다는 **기대** |
| 강도 | 별점으로 좋고 싫음 구분 | 항상 긍정, 강도 없음 |

**기각 — 찜을 약한 가상 별점(평균 +β)으로 S-1-1에 합산하는 안.** 보지 않은 영화에 가짜 평가를 주고,
평균 중심 합 안에 섞이면 **별점을 짜게 주는 사용자일수록 찜의 영향력이 커지는** 등 사용자마다 비중이 달라진다.
→ **찜에서는 장르·국가·감독에 대한 관심만 가져오고(사용자 제안), 평가 프로필과 따로 정규화한 뒤 고정 비율로 섞는다.**

### W-1-1. 장르·국가 관심도 — lift (카탈로그 대비 얼마나 많이 찜했나)

그냥 세면 **카탈로그에 원래 많은 장르(드라마)가 누구의 찜에서든 1등**이 된다 — 관심이 아니라 카탈로그 구성이다.

```
① share_w[x] = ( Σ_찜 w(x) + α × p_cat[x] ) / ( n찜 + α )      w = movie_genre / movie_country.weight
                                                               p_cat[x] = 카탈로그 전체의 x 비율
                                                               α = 5 (스무딩)
② I[x]       = max(0, share_w[x] / p_cat[x] − 1)
③ 정규화     I[x] / max(I)  → 0~1
```

| 예 | 카탈로그 | 내 찜 | lift | 해석 |
|---|---|---|---|---|
| 드라마 | 40% | 45% | 1.1 | 평균 수준 — 관심 아님 |
| 공포 | 8% | 30% | 3.8 | 강한 관심 |

- **α = 5** — 찜이 2개뿐인데 하나가 희귀 국가면 lift가 수십 배로 튄다. *"카탈로그 평균대로 찜한 5편이 미리 있다"* 고
  두고 계산한다. 찜이 쌓이면 영향이 사라진다.
- `p_cat`은 `MovieFeatureIndex` 재생성 시 함께 계산한다.

### W-1-2. 감독 관심도 — 반복 찜 (lift를 쓰지 않는다)

감독은 영화당 평균 1.08명이고 *"이 감독 작품이라 찜했다"* 가 흔해 포함한다(사용자 제안). 그러나 **lift는 맞지 않는다** —
감독 하나의 카탈로그 비율이 0.02% 수준이라 찜 1편에 lift가 수백 배가 되고, **작품 수가 적은 감독일수록 커져 다작 감독이 불리**하다.

```
I_D[감독] = Σ_찜 (1/N)              공동 연출 1/N 분배 (RA-4)
포함 조건: 같은 감독 작품 2편 이상 찜  ← 1편은 우연, 반복이 관심
정규화    I_D / max(I_D)
```

**배우는 넣지 않는다** — 찜 1편의 출연진 중 누구 때문에 찜했는지 알 수 없고, 인물 비율이 작아 lift도 성립하지 않는다.
배우 선호는 평가 기록에서만 온다.

### W-1-3. 결합

```
G_final = (1 − λ) × G + λ × I_G        λ = 0.3
C_final = (1 − λ) × C + λ × I_C
D_final = (1 − λ) × D + λ × I_D
A       = 평가 기반 그대로
P       = max(D_final, A)               ← S-1-2 그대로
```

- **평가 0.7 : 관심 0.3** — 직접 보고 매긴 평가가 더 확실한 신호.
- **평가 축이 전부 0이면 그 축은 λ = 1** — 그러지 않으면 찜만 한 신규 사용자의 T가 30%로 깎여 Q·Pop에 묻힌다.
- 평가가 낮은 장르라도 찜이 많으면 `0.3 × I`만큼 살아난다 — *"그래도 보고 싶어 한다"* 로 받아들인다.

### W-1-4. 규칙

| 규칙 | 값 | 이유 |
|---|---|---|
| 반영 개수 | **제한 없음** | 관심도가 비율이라 찜이 많아도 커지지 않고, λ가 비중을 고정한다. 많을수록 추정이 정확해진다 (사용자 판단) |
| 이미 본 영화 | 찜 계산에서 제외 | 별점이 더 정확한 신호, 이중 반영 방지 |
| 내 취향 추천 결과 | **찜한 영화 제외** | 이미 아는 영화 — 추천 슬롯 낭비 |
| 자연어 결과 | **포함 + `wished = true`** | 질의에 맞는 영화가 찜한 영화면 그 자체로 유용한 답 |
| 추천 이유 | 관심 항이 최대 기여면 "찜 목록에 많은 공포 장르" / "찜 목록에 봉준호 감독 작품이 많아요" | |
| 디버그 | 축별로 **평가 기여 / 관심 기여** 분리 표시 | λ 조정 근거 |

- **향후 후보** — ① 오래된 찜일수록 작게(기간 가중치) ② 찜 영화 임베딩 평균과의 유사도 항(장르로 안 잡히는 분위기 반영).
  운영해 보고 판단한다.
- **R-3에 주는 효과** — 가입 직후 찜 몇 개만으로 취향 추천이 개인화된다. R-3에는 *"기록도 찜도 없는 사용자"* 만 남는다.

## R-3. 콜드 스타트 — ✅ 기본 결과 유지 (2026-10-26)

**대상** — 평가 기록도 찜도 없는 사용자. (찜만 있는 사용자는 W-1로 개인화된다. 별점이 모두 같은 사용자도
S-1-1상 평가 축이 0이 되어 여기에 준한다.)

| 기능 | 동작 |
|---|---|
| 내 취향 추천 | T = 0 → `S = 0.20Q + 0.15Pop` — **평이 좋고 알려진 영화 순**. 제외 규칙·같은 감독 2편 상한·100편 페이징 그대로 |
| 자연어로 찾기 | `sim + Q` 로 정상 동작 (T 항만 0) |
| 추천 이유 | "평이 좋은 작품" / "많은 사람이 본 작품" (S-1-5 규칙이 그대로 이렇게 나온다) |

- **별도 로직을 두지 않는다** — S-1 공식이 T = 0에서 자연스럽게 이 결과를 낸다. 분기 없이 같은 코드 경로.
- **응답에 개인화 여부를 표시한다** — `personalized: false`(프로필의 모든 축이 0). 앱이 *"기록하거나 찜하면 취향 추천이
  시작돼요"* 같은 안내를 띄울 수 있게 한다.
- **게스트(비로그인)도 같은 결과를 받는다** (A-1-1, 사용자 제안) — 전역 공유 캐시 1개.
- **추후 업데이트 (사용자 결정)** — 가입 직후 온보딩(장르 몇 개 / 영화 몇 편 고르기)은 운영해 보고 판단한다.
  넣게 되면 **고른 장르·영화를 W-1의 관심 신호로 넣는 것이 가장 싸다** — 공식 변경 없이 입력만 늘어난다.

## A-1. 추천 API — ✅ 확정 (2026-10-26)

> **계약(엔드포인트·DTO·ErrorCode·화이트리스트)의 원본은 `controller-layer-spec.md` 5-14.** 여기는 결정 근거만 남긴다.

### A-1-1. 경로·인증

| 엔드포인트 | 인증 | 근거 |
|---|---|---|
| `GET /api/recommendations/for-you` | **비로그인 허용** (게스트 결과) | 콜드 스타트 결과(R-3)가 곧 게스트 결과 — 외부 비용 0, 비로그인 첫 화면을 채운다 (사용자 제안) |
| `GET /api/recommendations/search` | 로그인 필수 | 외부 비용 · 사용자별 호출 제한 · 이미 본 영화 제외에 사용자가 필요 |
| `POST /api/admin/embeddings/sync` · `GET /api/admin/recommendations/debug` | ADMIN | |

- `/api/recommendations/` — 5-0-F상 본인 상태 조회는 주체를 경로에 넣지 않고, `/api/movies/**`는 공개 GET 전용이다.
- 자연어는 **GET** — 조회 성격이고 기존 `GET /api/movies/search?query=`와 같다. 질의가 접근 로그에 남는 것은 기존 검색과 같은 수준으로 수용.
- ⚠️ **화이트리스트는 정확한 경로 하나** — `GET /api/recommendations/for-you`. `/**`로 열면 비용이 드는 `/search`까지 공개된다(리포트 5-8-A와 반대 방향의 실수).

### A-1-2. 응답 — 두 기능이 같은 `RecommendationResponse`

- `PageResponse` 재사용 — 순위 100편을 확정하므로 `totalElements`가 정확하다(4-6-E의 "필터 후 총계 불일치"가 없다).
- **추천 이유는 구조화** (`type`·`targetId`·`label`·`text`) — 앱이 아이콘 선택·인물 화면 이동을 문자열 파싱 없이 한다. `text`는 서버 생성(한국어 전용, 문구 변경에 앱 배포 불필요).
- 앱이 카드 컴포넌트 하나로 두 기능을 그린다. 자연어 전용 필드(`conditions`·`degraded`·`wished`)는 취향 추천에서 빈 값.

### A-1-3. 페이징·캐시 — "0페이지는 새로 계산, 그 뒤는 캐시"

- **0페이지 = 항상 재계산 후 캐시 교체** — 기록·찜 직후 화면 재진입/당겨서 새로고침이 0페이지라 **방금 본 영화가 남지 않는다.** 시청 기록 쪽에 캐시 무효화 이벤트를 걸지 않아 도메인 결합이 없다.
- **1페이지~ = 캐시 슬라이스** — 스크롤 중 순서가 흔들리지 않는다(S-1-6).
- **게스트 · 기록도 찜도 없는 사용자 = 전역 공유 캐시 1개** — 결과가 누구에게나 같다. 기동 시 + 06:00 인덱스 재생성 직후에만 계산하고 **0페이지도 재계산하지 않는다.** ⚠️ 인증·호출 제한이 없는 공개 경로에서 요청마다 1.3만 편을 채점하게 두면 반복 호출만으로 CPU를 소모시킬 수 있다.
- **질의 임베딩 캐시는 사용자와 무관하게 공유** — 질의 벡터에 사용자 정보가 없다.
- 캐시 상한이 작은 이유는 힙 640MB (결과 1,000개 ≈ 10MB, 임베딩 1,000개 ≈ 3MB).

### A-1-4. 호출 제한 — 자연어만, **실제 Gemini 호출만** 센다

프로젝트에 호출 제한이 없지만(security-spec L-1) 이 경로는 **외부 비용이 드는 첫 사용자 경로**라 최소 장치를 둔다.
캐시 적중·1페이지 이후는 세지 않는다. **분당 10 · 일 200 / 사용자**, Caffeine 인메모리(단일 인스턴스 전제 — security-spec과 같다).
마지막 방어선은 Google 할당량 상한(`deploy-spec.md` 11-A).

### A-1-5. 대체 결과 (`degraded`)

Gemini 실패·3초 타임아웃·벡터 인덱스 비어 있음 → **취향 추천 공식 결과**로 대체. 추출 조건(Q-1 하드 필터)은 유지,
`degraded: true`로 앱이 안내를 띄운다. **대체 결과는 캐시하지 않는다**(다음 요청에서 재시도). 호출 제한 초과는 대체하지 않고 429.

### A-1-6. 감사 로그

| 동작 | `AdminAction` | 근거 (admin-spec BD-2) |
|---|---|---|
| 임베딩 수동 실행 | `EMBEDDING_SYNC` | 관리자 쓰기 API 전부 |

### OP-1-3. 적재 후 무료 tier로 버틸 수 있는가

| 사용처 | 일 사용량 |
|---|---|
| 06:00 변경분 | 0~50편 |
| 자연어 질의 | **새로운 질의만** (질의 임베딩 캐시 24시간·사용자 공유, `page ≥ 1` 미호출) |
| 여유 | 새로운 질의 약 950건/일 |

**캡스톤 규모(사용자 수십 명, 발표 시 동시 수십 명)는 충분하다.** 한도를 넘어도 `degraded` 대체(5-14-F)로 앱은 멈추지 않는다.

**막히는 경우 3가지**

1. **대량 텍스트 변경** — 인물 한글명 일괄 보강(카탈로그 보강 C-3, 약 2,400명)·템플릿 변경은 수천 편의 해시를 바꿔
   재임베딩에 며칠이 걸리고, 그동안 배치가 질의 몫을 잠식한다. **발표·시연 일정을 피해서** 한다.
2. **초기화 시각** — 위 OP-1-1. 배치 시각과 함께 관리한다.
3. **사용자 질의의 데이터 정책** — 무료 tier는 보낸 내용이 제품 개선에 쓰일 수 있다(E-4-6). 캡스톤 시연·테스트는 수용,
   **스토어 출시(M5) 전 유료 전환 + `deploy-spec.md` 11-A**. 그때 개인정보 처리방침 문구도 확인한다.

| 시기 | 운영 |
|---|---|
| 적재 약 14일 | 무료 tier, 17:10 배치, 1회 800편 |
| 적재 후 ~ 캡스톤 발표 | 무료 tier. 대량 재임베딩은 발표 일정 회피 |
| **출시(M5) 전** | **유료 전환** + 11-A 체크리스트 |

### OP-1-4. 사용량이 커지면 — 폐기 전에 단계가 있다

**유료 tier에서 한도·비용은 폐기 사유가 되기 어렵다.** 질의 1건 ≈ 30토큰이라 *사용자 10만 × 월 10회 = 월 100만 건 ≈ $6*
(캐시로 실제는 더 낮다). 유료 한도는 무료보다 훨씬 높고 결제 이력에 따라 오르며 상향 신청도 가능하다(정확한 수치는 전환 시 공식 표 확인).

**먼저 막히는 곳은 Gemini가 아니라 우리 쪽이다** — 앱 전체의 확장 과제다.

| 지점 | 한계 | 대응 |
|---|---|---|
| EC2 `t4g.small` 2GB | 동시 접속 증가 시 CPU·메모리 | 인스턴스 상향 (D-1의 4GB 경로) |
| 호출 제한·캐시가 인메모리 | 서버 2대 이상이면 카운트가 갈라진다 | Redis (security-spec L-1과 같은 과제) |
| 메모리 전수 비교 | 영화 수에 비례(사용자 수와 무관). 10만 편까지 질의당 수십 ms | 그 이상이면 벡터 DB 검토 |

**단계별 대응 경로**

| 단계 | 상황 | 대응 |
|---|---|---|
| 1 | 지금 ~ 출시 초기 | Gemini 유료 + 캐시 + 사용자별 호출 제한 |
| 2 | 비용·외부 의존이 부담 | **서버 상주 모델로 교체** — `EmbeddingClient` 구현 하나(`OnnxEmbeddingClient`, 예: multilingual-e5-small) + 4GB 인스턴스 + 전량 재임베딩. 호출 비용·한도·외부 의존 0, 한국어 품질은 다소 하락 (M-1 기각 사유가 그대로 대가) |
| 3 | 자연어 기능이 쓰이지 않음 | 그때 폐기 검토 — **사용량 데이터로** 판단 |

*"많이 쓰여서 폐기"* 가 아니라 *"많이 쓰이면 2단계, 안 쓰이면 3단계"* 다. 자연어는 하이브리드 추천의 차별점이고, 이용 증가는 잘 작동한다는 신호다.
