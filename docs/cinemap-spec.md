## C-1. 화면 기본 구성 — ✅ B′ (한 화면 스크롤 + 지도 미리보기)

```
CineMap 탭 (세로 스크롤)
├── 박스오피스        가로 목록 5편 + "더보기" → 전체 10위 화면
├── 내 주변 극장
│   ├── 지도 미리보기   마커 표시, 끌기·확대 꺼짐 — 탭하면 전체 화면 지도
│   ├── 가까운 극장 5곳
│   └── [지도에서 모두 보기]
└── (전체 화면 지도)  지도 + 바텀시트 목록 + 극장 카드 [예매하기] [길찾기]
```

| 결정 | 이유 |
|---|---|
| 원안 B(한 화면) 유지 — 사용자 의도 | 박스오피스와 극장을 한눈에 |
| **지도는 미리보기(조작 불가)** | 스크롤 화면 안의 조작 가능한 지도는 **세로 스크롤과 지도 끌기가 충돌**한다(§13.2 위험도 "큼", Android WebView에서 심함). 미리보기는 탭만 받는다 |
| 탐색은 **전체 화면 지도** | 상단 탭안(A)에도 어차피 필요한 화면이라 추가 비용이 아니다 |
| 박스오피스 가로 목록 5 + 더보기 | 가로 스크롤은 세로 스크롤과 충돌하지 않는다 |
| **위치 권한은 미리보기 영역의 "내 위치로 보기"에서** | 처음엔 기본 위치(서울시청)로 보여 준다 — 박스오피스만 보는 사람은 권한 요청을 받지 않는다 |

- **기각 — A안(상단 탭 `박스오피스 | 내 주변 극장`)** — 충돌은 없지만 한눈에 보기를 잃는다. B′가 둘 다 얻는다.
- **기각 — 카카오 정적 지도 이미지로 미리보기** — 가볍지만 일 무료 1,000건 초과 시 건당 과금, 화면 진입마다 호출하는 구조와 맞지 않는다.

## C-2. 지도 API — ✅ 카카오 JS SDK + WebView

| 비교 | 카카오 JS + WebView (채택) | 네이버 네이티브 | 구글/애플 |
|---|---|---|---|
| 한국 지도 | 최상 | 최상 | ⚠️ 구글은 2026-02 고정밀 지도 반출 **조건부 허가**, 반영 시점 불확실 |
| 조작감 | WebView(초기 로딩 0.5~1.5초) | 네이티브, 최상 | 네이티브 |
| 계정 | **기존 카카오 디벨로퍼스 앱에 지도 활성화** | 네이버 클라우드 가입 + 결제수단 | 구글 클라우드 |
| 비용 | 계정에서 **처음 지도를 활성화한 앱에 무료 쿼터**(2026-07-21 정책) | 종량제, 모바일 무료 구간 미확인 | 월 크레딧 |
| 새 외부 의존 | 없음 (로그인과 같은 업체) | 네이버 추가 | 구글 추가 |

- **근거** — 새 업체·결제·약관 없음. B′ 구성이면 WebView의 최대 약점(제스처 충돌)이 미리보기에서 사라진다. CineMap은 일정이 밀리면
  가장 먼저 잘라 낼 기능(기획노트 "잘라낼 순서")이라 설정 비용이 작은 쪽이 맞다.
- **교체 경로 유지** — §13.3 격리 인터페이스. 네이버 네이티브로 바꾸는 비용 반나절~1일. Dev Client 전환(9/11)이 끝나 §13.4의
  "편도 전환" 비용도 사라졌다. 인터페이스에 **`interactive: boolean`**(미리보기 모드) 추가.
- **카카오 네이티브 SDK v2 기각** — 관리되는 RN 래퍼가 없어 네이티브 모듈을 직접 만들어야 한다.

**카카오 디벨로퍼스 설정 (사용자 작업)**

1. 기존 CineMory 앱에서 **카카오맵 활성화** — ⚠️ 무료 쿼터는 계정에서 처음 활성화한 앱에 붙는다. 다른 테스트 앱에서 먼저 켜지 않는다.
2. **JavaScript 키** 확인 + **Web 플랫폼 도메인 등록** — WebView가 로컬 HTML을 띄울 때의 `baseUrl`과 맞춘다(구현 단계 확인).
3. **REST API 키** 확인 — 백엔드 주소 → 좌표 변환(C-4-4)용. 서버에만 둔다.

## C-3. 극장 데이터 원천 — ✅ 행정안전부_문화_영화상영관 조회서비스

| 항목 | 내용 |
|---|---|
| 위치 | 공공데이터포털 **15154848** (REST, JSON/XML) |
| 범위 | 전국 자치단체 영화상영관 인허가 통합 |
| 갱신 | 일간 |
| 한도 | 개발 계정 일 10,000건 |
| 좌표 | **Bessel 중부원점 TM(EPSG:5174)만**, 위경도 없음. **빈 값인 행이 있다**(실측) |
| `totalCount` | **5,244** (2026-10-27, 폐업 포함) |

- **기각 — "한국문화정보원_전국 연극장 및 소극장 데이터"** — 연극 공연장이다.
- 기획노트 (5)의 *"EPSG:5174 → WGS84 변환 필수"* 가 이 데이터를 가리킨다.
- 기존 `TheaterSeedData` 주석의 *"전국영화상영관표준데이터 1행"* 은 이 원천으로 대체한다.

### C-3-1. ⚠️ 실측 — 응답 샘플 10건 (2026-10-27)

**① 한 행 = 극장이 아니라 상영관(관) 하나** — "롯데시네마 속초 1관"~"5관"이 각각 별도 행이다. 5,244는 상영관 수다.
그대로 넣으면 같은 자리 마커가 관 수만큼 겹친다. → **극장 단위로 묶는다**(C-4-2).

**② `MNG_NO`가 전국 고유가 아니다** — `CDFF4220002026000005`가 속초 5관과 검단아라 1관에 둘 다 있다. 자치단체마다 번호를 따로 매긴다.
원천 행 식별은 `OPN_ATMY_GRP_CD + MNG_NO`.

**③ 좌표 빈 행** — 검단아라 5개 관은 `CRD_INFO_X/Y`가 `""`. → **주소 → 좌표 변환이 기본**(C-4-4).

**④ 같은 극장의 관끼리 주소 상세가 다르다** — 검단아라 6관만 도로명 주소에 "18층"이 붙어 있다. 상세 주소로 묶으면 갈라진다.

### C-3-2. 사용할 필드

| 필드 | 예 | 용도 |
|---|---|---|
| `OPN_ATMY_GRP_CD` | `4231000` | 자치단체 코드 — 묶음 키의 일부 |
| `MNG_NO` | `CDFF4220002026000005` | 자치단체 안에서만 고유 |
| `BPLC_NM` | 롯데시네마 속초 3관 | 극장명 · 체인 판정 |
| `SALS_STTS_CD` / `SALS_STTS_NM` | `01` / 영업/정상 | **`01`만 적재** |
| `DTL_SALS_STTS_NM` | 영업중 | 참고 |
| `PRFRPLC_SHP_SE_NM` | 영화관 | 영업 형태 — 다른 값(자동차극장 등) 분포는 dryRun으로 확인 |
| `ROAD_NM_ADDR` | 강원특별자치도 속초시 중앙로121번길 28, 센텀마크빌딩 제엠-301호 (금호동) | 주소 · 묶음 키 · 좌표 변환 |
| `LOTNO_ADDR` | 강원특별자치도 속초시 금호동 473-235 센텀마크빌딩 | 도로명이 없을 때 대체 |
| `CRD_INFO_X` / `CRD_INFO_Y` | `339101.58` / `523440.60` | EPSG:5174, 마지막 대체 수단 |
| `DAT_UPDT_PNT` | 2026-10-08 21:10:40 | 향후 변경분 동기화(C-5) |

**쓰지 않는다** — 좌석 수 필드가 없다(`theater.seat_count`는 null). 층수·통로 폭·청소년실 등 인허가 항목은 화면 요구가 없다.

## C-4. 극장 적재 설계 — 🟡 초안 (B-9 해소)

### C-4-1. 입력 방식 — 파일이 아니라 API를 서버가 직접 호출

B-9의 *"멀티파트 업로드 vs 서버 파일"* 문제가 사라진다. KOFIC 박스오피스와 같은 구조다.

```
POST /api/admin/theaters/seed[?dryRun=true]
  TheaterSeedService (트랜잭션 없음)
   1. PublicDataTheaterClient — 전 페이지 순회 (numOfRows 100 → 약 53회)
   2. 영업 중(SALS_STTS_CD=01) + 영업 형태 필터
   3. 극장 단위 묶기 (C-4-2)        → 극장명 · 체인 · 상영관 수
   4. 좌표 결정 (C-4-4)             → 카카오 주소 검색 → 지번 → TM 변환
   5. dryRun이면 통계만 반환(C-4-6), 아니면 TheaterPersister(@Transactional) upsert
```

- HTTP 호출은 트랜잭션 밖, 저장만 별도 빈 — tmdb-sync 6-4 원칙.
- `global/infra/publicdata/PublicDataTheaterClient` — `tmdb`·`kofic`과 같은 위치. 타임아웃 connect 2s / read 5s.
- 키 — `publicdata.service-key`(운영 `PUBLICDATA_SERVICE_KEY`), `kakao.rest-api-key`(운영 `KAKAO_REST_API_KEY`). `cinemory.env.example`·런북 대응표에 추가.
  ⚠️ 공공데이터포털 키는 **Decoding 키를 쓰고 HTTP 클라이언트가 인코딩**하게 한다(Encoding 키를 넣으면 이중 인코딩).
- 실행 중 플래그 — 시드·resync·임베딩과 **분리**(호출 대상이 다르다). 실행 중이면 409 `SEED_ALREADY_RUNNING` 재사용 여부는 구현 시 판단.
- 감사 로그 `THEATER_SEED` (dryRun은 기록하지 않는다 — 쓰기가 없다).

### C-4-2. 극장 단위로 묶기 — **주소 기준**

| 후보 | 판정 |
|---|---|
| 극장명에서 "N관"을 떼고 묶기 | ⚠️ 이름이 지저분하다 — "IMAX관"·"4DX관"·"골드클래스" 등 "N관"이 아닌 관 이름, 표기 흔들림("CGV"/"씨지브이"). 떼는 규칙이 끝없이 늘어난다 |
| **도로명 주소의 "도로명 + 건물번호"로 묶기 (채택)** | 같은 극장의 관은 같은 건물에 있다. 상세(동·호·층·괄호)를 떼면 ④의 "18층" 차이도 흡수된다 |

```
묶음 키  = OPN_ATMY_GRP_CD + "|" + 주소 기준부
주소 기준부 = ROAD_NM_ADDR에서 첫 쉼표 앞 + 괄호 제거 → "강원특별자치도 속초시 중앙로121번길 28"
            (도로명이 비면 LOTNO_ADDR에서 번지까지)
```

| 묶은 극장의 값 | 결정 |
|---|---|
| `name` | 그룹 안 이름들을 정규화(C-4-3)한 뒤 **가장 많이 나온 값** |
| `chain_name` | 이름 앞부분 사전 매칭(C-4-3) |
| `screen_count` | **그룹의 행 수** (영업 중인 관 수) — 기존 컬럼에 그대로 |
| `seat_count` | null (원천에 없음) |
| `address` | 주소 기준부 (상세 제외) |
| `source_code` | 묶음 키 |

- ⚠️ **한 건물에 극장이 둘**(쇼핑몰에 CGV·메가박스)이면 하나로 묶인다 — 드물 것으로 보지만 **dryRun이 "한 그룹 안에 체인이 둘 이상"인 경우를 따로 보고**한다.
  있으면 묶음 키에 체인을 추가한다.
- 스키마 — `theater.source_code varchar(30)`에 묶음 키가 들어가지 않는다 → **`varchar(255)`로 확장**(Flyway, 확장 마이그레이션).

### C-4-3. 극장명 정규화 · 체인 판정 — dryRun 후 확정

**시작 규칙**

1. 앞뒤 공백 제거, 연속 공백 1개
2. **끝의 관 표기 제거** — `\s*(제)?\d+(관|상영관)$`, 그리고 끝 토큰이 사전의 특별관(IMAX·4DX·SCREENX·골드클래스·샤롯데·부티크·리클라이너 등)+"관"이면 제거
3. 그룹 안 최빈값을 극장명으로

**체인 사전 (시작)**

| `chain_name` | 이름 앞부분 |
|---|---|
| CGV | `CGV`, `씨지브이` |
| 롯데시네마 | `롯데시네마` |
| 메가박스 | `메가박스`, `MEGABOX` |
| 씨네Q | `씨네Q`, `씨네큐` |
| 기타 | 그 외 (독립·예술영화관 등) |

- 규칙이 *맞는지는* 샘플 10건으로 알 수 없다 → dryRun의 "정규화 후에도 이상한 이름" 목록으로 보완한다.

### C-4-4. 좌표 결정 — 카카오 주소 검색 우선

| 순서 | 방법 | 비고 |
|---|---|---|
| 1 | **주소 기준부**를 카카오 로컬 **주소 검색**(REST) → WGS84 | **지도와 같은 카카오 데이터라 마커가 지도 위 건물에 정확히 맞는다** |
| 2 | 1 실패 → `LOTNO_ADDR` 기준부로 주소 검색 | |
| 3 | 2 실패 + TM 좌표 있음 → **EPSG:5174 → EPSG:4326** 변환(`proj4j`) | ⚠️ Bessel 타원체 변환 파라미터가 틀리면 **수백 m씩 어긋나도 오류 없이 저장**된다 — 단위 테스트로 알려진 지점 1곳 이상을 고정한다 |
| 4 | 모두 실패 | 적재하지 않고 `WARN` + dryRun 실패 목록 |

- 호출량 — 극장 수(수백) × 1~2회, 1회성. 카카오 로컬 무료 쿼터 안.
- 주소 → 좌표는 **그룹당 1회**(관마다 하지 않는다).

### C-4-5. 저장 정책 — 기존 "있으면 건너뛰기"를 바꾼다

기존 `TheaterSeedService.seedAll`은 *"이미 있는 `source_code`는 건너뛴다(극장 속성은 거의 안 변한다)"* 였다. 공공 API는 매일 갱신되고
**관 증설·폐관이 `screen_count`·존재 여부를 바꾼다.** → **upsert**(있으면 이름·체인·주소·좌표·관 수 갱신)로 바꾼다.
`Theater`에 `updateFromSource(...)` 하나를 연다(Setter 금지 원칙 — 의도가 드러나는 메서드 하나).

- **폐업 처리는 C-5에서** — `theater`를 FK로 참조하는 테이블이 없다(확인 2026-10-27). 원천에서 사라진 극장을 삭제해도 무결성 문제는 없다.

### C-4-6. dryRun — 적재 전에 실측한다

`POST /api/admin/theaters/seed?dryRun=true` → 저장 없이 200 `TheaterSeedReport`.

| 항목 | 용도 |
|---|---|
| 전체 행 · 영업 중 행 · 묶은 극장 수 | 규모 |
| `PRFRPLC_SHP_SE_NM`별 건수 | 영업 형태 필터 결정(자동차극장 등) |
| 체인별 극장 수 (`기타` 포함) | 사전 보완 |
| **정규화 후 이름이 그룹 안에서 갈린 그룹** 상위 50 | 정규화 규칙 보완 |
| **한 그룹에 체인이 둘 이상**인 그룹 | 묶음 키 보완 여부 |
| 관 수 분포 (1관 극장 수 등) | 소규모 상영 시설 판단 |
| 좌표 결정 경로별 건수 (주소 / 지번 / TM / 실패) + 실패 목록 | 좌표 품질 |
| 샘플 20개 극장 (최종 값) | 눈으로 확인 |

**한 번 만들어 두면 재동기화 전 검증 도구로 계속 쓴다.**

## C-5. 폐업 처리 · 재동기화 — ✅ 확정 (2026-10-27)

### C-5-1. 폐업 = 삭제가 아니라 숨김 (`closed_at`)

**극장 단위 폐업은 원천에 직접 없다** — 원천은 상영관 단위라 관이 하나씩 폐업 처리된다. 극장의 폐업은
*"그 묶음에 영업 중인 관이 하나도 남지 않아 묶음 자체가 사라진 것"* 으로 판정한다.

| 안 | 판정 |
|---|---|
| 삭제 | ❌ C-8의 `booking_url`(관리자 입력)이 사라지고, 원천이 하루 잘못 오면 극장이 지워진다 |
| **숨김 (채택)** | ✅ 다시 나타나면 자동 복구, 관리자 입력 보존. FK 참조가 없어 삭제도 가능하지만(확인 2026-10-27) 이득이 없다 |

```sql
ALTER TABLE theater ADD COLUMN closed_at DATETIME(6) NULL;   -- V34(booking_url)와 같은 마이그레이션에 묶어도 된다
```

| 상황 | 처리 |
|---|---|
| 동기화에서 묶음이 사라짐 | `closed_at = now` |
| 숨긴 극장이 다시 나타남(같은 `source_code`) | `closed_at = null` (자동 복구) |
| `GET /api/theaters/nearby` | **`closed_at IS NULL`만** |
| 관리자 극장 목록(C-8-2) | 숨긴 극장도 보인다 + "폐업" 필터 |

- 물리 삭제는 하지 않는다 — 극장 약 720곳이라 쌓여도 부담이 없다. **2026-11-01부터 제약으로 강제** — `watch_record.theater_id`가 `ON DELETE RESTRICT`로 참조한다(`service-layer-spec.md` 4-3-C). 숨김 필터는 "새로 고를 수 있는 극장"(주변 · 검색)에만 걸고, 기록에서 극장을 읽는 조회에는 걸지 않는다.
- 엔티티: `Theater.close(Instant)` · `Theater.reopen()` — 의도가 드러나는 메서드(Setter 금지).

### C-5-2. ⚠️ 원천 사고 방지 — 장치 2개

숨김이라도, 공공 API가 일부 페이지만 주고 끊기면 **멀쩡한 극장 수백 곳이 한꺼번에 숨겨진다.**

**① 전부 받은 뒤에만 반영** — 현재 구현은 이미 *전 페이지 수집 → 묶기 → `TheaterPersister.upsertAll` 한 트랜잭션* 구조다. 여기에:

- **수신 행 수 검증** — 받은 고유 행(`OPN_ATMY_GRP_CD+MNG_NO`) 수 + 중복 수 == `totalCount`가 아니면 **아무것도 반영하지 않고 중단**
  (`TheaterSeedReport.aborted = true`, 사유). `MAX_PAGES` 도달도 같은 처리.
- 숨김·복구도 **같은 트랜잭션**에서.

**② 숨김이 너무 많으면 숨김만 보류** — 한 번에 숨길 극장이 **max(영업 중 극장의 5%, 10곳)** 을 넘으면 숨김은 건너뛰고
upsert(신규·갱신)·복구만 반영한다. `WARN` + 보고서 표시. 진짜 대량 폐업이면 관리자가 `?allowMassClose=true`로 다시 실행.
기준값은 프로퍼티(`cinemory.theater.sync.mass-close-ratio: 0.05`, `mass-close-min: 10`).

### C-5-3. 재동기화 — 주 1회 스케줄 + 수동

| 근거 | 내용 |
|---|---|
| 원천 갱신 | 매일 |
| 실제 변화 | 개관·폐관·관 증설은 월 단위로 드묾 |
| 비용 | 공공 API 약 53회(일 한도 10,000) + 카카오는 아래 재사용으로 거의 0 |

- **스케줄: 매주 월요일 04:00** (`cinemory.theater.sync.cron`, Asia/Seoul) — 05:00 박스오피스보다 먼저 끝난다.
- **수동: 기존 `POST /api/admin/theaters/seed`**(`dryRun`·`allowMassClose`) 그대로. 실행 플래그를 스케줄과 공유(409 `THEATER_SEED_ALREADY_RUNNING`).
- **좌표 재사용** — 기존 극장이고 **주소 기준부가 같으면 저장된 좌표를 쓰고 카카오를 호출하지 않는다.** 신규·주소 변경 극장만 C-4-4 경로.
- **변경분 동기화(`DAT_UPDT_PNT`) 기각** — 전체도 53회라 복잡도만 늘고, 전체를 받아야 "사라진 극장"을 판정할 수 있다.
- 감사 로그 — 스케줄 실행은 관리자 행위가 아니라 남기지 않는다(애플리케이션 로그만). 수동 실행은 기존 `THEATER_SEED`.

### C-5-4. 보고서 추가 (dryRun · 실행 공통)

| 항목 | 용도 |
|---|---|
| `newTheaters` | 이번에 새로 생긴 극장 |
| `closedTheaters` | 이번에 숨긴 극장 |
| `reopenedTheaters` | 이번에 복구한 극장 — 원천 흔들림 감지 |
| `massCloseHeld` | ② 장치 발동 여부와 보류된 건수 |
| **`closedWithBookingUrl`** | `booking_url`이 있는데 숨겨진 극장 — **관리자 확인 대상** |
| `aborted` · `abortReason` | ① 장치 발동 |
| `geocodeReused` · `geocodeCalled` | 좌표 재사용 효과 |

**알고 감수하는 것** — 극장 주소가 바뀌면(도로명 변경 등) 묶음 키가 달라져 *옛 극장 숨김 + 새 극장 생성*이 되고 `booking_url`이
옮겨지지 않는다. 이름·위치 유사도로 자동 이전하는 안은 오판 위험으로 기각 — `closedWithBookingUrl` 목록으로 관리자가 확인한다.

## C-6. 박스오피스 — ✅ 확정 (2026-10-27)

### C-6-1. 화면 (시안 「CineMap 화면 시안」)

| 위치 | 내용 |
|---|---|
| CineMap 탭 상단 | **가로 목록 5편** + "더보기". 섹션 제목 아래 "{M월 D일} · 일별 관객 기준" |
| 카드 | 포스터 120×180(모서리 8) 위 **순위 숫자**(32, 흰색, 아래쪽 어둡게 깐 그라데이션 위) · 제목 2줄 · "누적 {n}만" · 순위 변동 |
| 더보기 화면 | 1~10위 목록 — 순위 · 포스터 44×66 · 제목 · "일 관객 {n}만 · 누적 {n}만" · 순위 변동 · 출처 "영화진흥위원회" |

| 순위 변동 | 표시 |
|---|---|
| `isNew = true` | **NEW** 배지 (포스터 위, `shadowDeep` 바탕 흰 글자) |
| `rankChange > 0` | ▲n — `shadowDeep` |
| `rankChange < 0` | ▼n — `mutedForeground` |
| 0 · null | 표시 안 함(카드) / "–"(더보기) |

- `rankType`은 **`DAILY` 고정**, `targetDate` 생략(= 최신 집계일, 4-7). 주간·주말 전환은 범위 밖.
- 관객 수는 만 단위 반올림("12.4만", "1,204만"). 1만 미만은 "8,213명".

### C-6-2. ⚠️ 미등록 영화 (`linked = false`, `movieId = null`) — 자동 등록 + 남는 것만 비활성

**원인** — 수집(05:00)·재매칭(05:30)은 자동인데 **영화를 새로 만드는 역방향 시드(D-2)가 수동**이라, 새 개봉작이 `movie`에 없어 연결되지 않는다.

**자동화 (사용자 결정)**

```
05:00 박스오피스 수집 → 05:15 역방향 시드 (그날 미매칭 영화만, 최대 20편) → 05:30 재매칭
```

- 기존 `MovieSeedService.seedFromBoxOffice` 재사용 — 대상만 **그날 수집분의 미매칭 제목**으로 좁힌다(전량 아님).
- cron은 프로퍼티(`cinemory.boxoffice.reverse-seed-cron`), 상한은 `reverse-seed-daily-limit: 20`.
- TMDB 429 규칙(6-5 `break`)·시드 실행 플래그 공유 그대로. 수동 시드와 겹치면 스케줄 쪽이 건너뛰고 `INFO`.
- 새 영화는 다음 임베딩 배치에서 벡터가 생겨 추천에도 들어간다.
- **앱에서 누를 때 등록하는 안 기각** — 박스오피스엔 TMDB ID가 없어 제목 검색이 필요하고 동명 영화를 잘못 고를 수 있다. 서버 배치는 개봉일까지 비교한다.

**남는 것** — 8월 실측 역방향 매칭률 90.7%. 재개봉작·TMDB에 없는 국내 독립영화·표기 차이는 실패한다 →
카드·행을 **흐리게(불투명도 0.6), 누를 수 없게**, 포스터는 대체 이미지. 더보기 행에는 "앱 미등록" 문구.

### C-7-2. 전체 화면 지도

| 요소 | 규칙 |
|---|---|
| 상단 | 뒤로(44, 흰 원) · **"이 지역에서 다시 검색"**(지도를 움직였을 때만 표시, 누르면 지도 중심 + 화면 반경으로 재조회) |
| 우측 | 내 위치 버튼(44) — 시트 위에 띄운다 |
| 마커 | **단일 색**(`shadowDeep`) 핀. 선택된 극장은 더 크고 진한(`#14524D`) 핀 + 이름 라벨, 나머지는 흐리게 |

| 목록 시트 | 높이 약 300(접힘·펼침 2단), "이 지역 극장 {n}곳" · 가까운 순 |

- **체인별 마커 색 기각** — 브랜드 색 사용 문제, 4~5색은 지도 위에서 구분이 어렵다. 체인은 카드 글자로 구분.
- **움직일 때마다 자동 재조회 기각** — 호출이 늘고, 목록을 보는 중 결과가 바뀐다.
- 재조회 반경 = 화면 대각선의 절반(상한 `max-radius-meters` 50km), 결과 상한 `max-result-size` 50 — 넘으면 시트에 "지도를 확대하면 더 보여요".
- **자동차극장은 구분하지 않는다** (사용자 결정, 2026-10-27).

## C-8. 예매 · 길찾기 — ✅ 확정 (2026-10-27)

### C-8-1. 예매 링크 — `theater.booking_url` 우선, 없으면 체인 기본, 둘 다 없으면 버튼 없음

공공데이터에는 "온라인 예매 가능 여부"가 없다. **체인 극장은 체인 예매로 보내고, 독립영화관은 극장별로 직접 등록한다**
(사용자 결정 — 독립영화관 온라인 예매가 생각보다 많다).

| 순서 | 출처 | 버튼 문구 | `bookingSource` |
|---|---|---|---|
| 1 | **`theater.booking_url`** (관리자 입력) | "온라인 예매" | `THEATER` |
| 2 | 체인 기본 URL (서버 설정) — CGV · 롯데시네마 · 메가박스 · 씨네Q | "{체인}에서 예매" | `CHAIN` |
| 3 | 없음 (독립·기타에 등록 없음) | **버튼 없음** | `null` |

- **서버가 최종 URL을 정해 내려준다** — 응답 `bookingUrl`·`bookingSource`. 체인 기본 URL은 서버 설정
  `cinemory.theater.chain-booking-urls`(설정 키 → https URL, 키는 ASCII `cgv`·`lotte-cinema`·`megabox`·`cine-q` — 한글 키는 Boot가 걸러 바인딩되지 않는다, 2026-10-28). *(앞서 "앱 상수"로 정했던 것을 바꾼다 — 극장별 값과 체인 기본값의
  우선순위를 한 곳에서 판정해야 해서다.)*
- **체인 링크는 체인 예매 페이지까지** — 극장이 미리 선택된 페이지는 체인 내부 극장 코드가 있어야 하는데 공공데이터에 없다.
  그래서 문구가 "{체인}에서 예매"다. 극장 단위로 보내고 싶은 체인 극장은 `booking_url`을 넣으면 1순위로 덮는다.
- **https 링크만 연다**(`Linking.openURL`) — 체인 앱이 있으면 OS가 앱으로 여는 경우가 많고, 없으면 브라우저. 앱 URL 스킴은
  체인이 바꾸면 조용히 깨지고 Android는 설치 확인에 매니페스트 `queries`가 필요해 쓰지 않는다.

### C-8-2. `theater.booking_url` (V34)

```sql
ALTER TABLE theater ADD COLUMN booking_url VARCHAR(500) NULL;
```

| 규칙 | 내용 |
|---|---|
| 입력 | **관리자만** — `PATCH /api/admin/theaters/{id}/booking-url` (`{ "bookingUrl": "https://…" }`, null이면 삭제) |
| 검증 | `https://`로 시작 · 최대 500자 · 공백 불가 — 위반 400 `INVALID_BOOKING_URL` |
| 극장 찾기 | `GET /api/admin/theaters?query=&chain=&hasBookingUrl=` (페이징, 이름·주소 검색) |
| ⚠️ 시드와의 관계 | **시드 upsert는 `booking_url`을 건드리지 않는다** — `title_ko`·`name_ko`와 같은 원칙(동기화는 원천 필드만 덮고 관리자 보강분은 보존) |
| 감사 로그 | `THEATER_BOOKING_URL_UPDATE` (이전 값 → 새 값) |
| 엔티티 | `Theater.updateBookingUrl(String)` — 검증은 서비스, 엔티티는 대입만(정적 팩토리·Setter 금지 원칙) |
| 관리자 화면 | 극장 목록(검색·"예매 링크 없음" 필터) + 상세에서 URL 입력 — admin-spec에 화면 추가 |

- 폐업은 숨김(C-5-1)이라 `booking_url`이 보존된다. 숨겨진 극장의 링크는 보고서 `closedWithBookingUrl`로 확인한다.

### C-8-3. 길찾기 — 카카오맵 웹 링크

```
https://map.kakao.com/link/to/{극장명},{위도},{경도}
```
