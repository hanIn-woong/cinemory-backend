## 1. 왜 리포트를 먼저 하는가

기획노트 4절이 이미 정리해 뒀다 — **M3는 준비 상태가 전혀 다른 두 덩어리**다.

| | 설계 상태 |
|---|---|
| **M3-a 리포트** | ✅ 가중치 공식·집계 쿼리 패턴까지 완료(2-4). **SQL 집계만으로 구현 가능** |
| M3-b 추천 | ❌ 백지. 임베딩 저장 위치조차 미결(R-2·R-4) |

그리고 **리포트의 집계 결과가 곧 추천의 입력**이다. 리포트를 먼저 만들면 R-1(선호도 입력
소스)이 실데이터로 검증되고, 그 위에 추천을 얹으면 된다. 데모 관점에서도 화면이 잘 나온다.

## 2. 이미 준비된 것 — M1이 입력을 완성해 뒀다

| 데이터 | 상태 | 근거 |
|---|---|---|
| `movie_genre.weight` (`1/N` 균등) | ✅ 적재 | tmdb-sync 6-3 |
| `movie_country.weight` (`(N+1)/(N²+1)`) | ✅ 적재, 대표국 판정 포함 | D-3 |
| `movie_actor.role_tier` + `RoleTier.weight` | ✅ 적재 | D-1 |
| **별점의 단일 출처 = `watch_record.rating`** | ✅ 확정 (v15, 2026-09-02) | 8절 R-1 · 2-3 |

**D-1이 M3를 위한 작업이었다.** 배우 가중치를 절대 순번(`0~4 LEAD` / `5~9 SUPPORTING` /
`10~20 MINOR` / `21~ EXTRA(0.0)`)으로 정하면서 **영화당 배우 선호 기여 총점이 출연진 수와
무관하게 5.6으로 고정**됐다. 이게 없었으면 출연진 200명짜리 영화가 집계를 통째로 왜곡한다.

**기준 쿼리 패턴** (2-4절, 선호 장르 예시 — 국가·배우도 동일 형태)

```sql
SELECT g.name, SUM(wr.rating * mg.weight) AS score
FROM watch_record wr
JOIN movie_genre mg ON wr.movie_id = mg.movie_id
JOIN genre g ON mg.genre_id = g.id
WHERE wr.user_id = ? AND wr.is_representative = TRUE AND wr.rating IS NOT NULL
GROUP BY g.id ORDER BY score DESC;
```

별점 없는 대표 기록은 `WHERE`에서 자연히 빠져 0으로 기여한다 — R-1이 미결로 남겼던
"평점 없는 기록의 가중치"에 대한 답이다.

### 2-1. 설계 확정에 쓴 실측값 (2026-09-11 측정)

세 쿼리가 RA-3·RA-4와 별점 버킷을 추측 없이 닫았다.

| 실측 | 결과 | 확정에 미친 영향 |
|---|---|---|
| `movie`의 `runtime` 결손 | **3 / 4,641 (0.065%)** | RA-3의 *"평균 보정 vs 주석 표기"* 논쟁이 소멸. 0으로 합산하고 주석도 달지 않는다 |
| 영화당 감독 수 | 평균 **1.0825명**, 공동 연출 **305편(6.6%)** | B안(`SUM(rating)`)과 C안(`1/N` 분배)의 실질 차이가 거의 없음이 확인됐다. 그럼에도 C안을 택했고, **근거가 성능에서 일관성으로 바뀌었다**(RA-4) |
| `watch_record.rating` 실제 분포 | **5~10 정수만**(0.5 단위 미사용, 당시 40건) | 별점 버킷을 **정수 1~10**으로 확정. §7.3 프론트 계약과 일치 |

> ⚠️ **실측 과정에서 검증 갭을 하나 찾았다** — 아래 9절 신규 항목 ①.

## 3. ★ 확정 사항 7건 (RA-1 ~ RA-7)

> 초판에서 미결로 남긴 항목이다. **2026-09-20 전부 확정.** 각 항목의 결론과 그 근거를 남긴다.

### RA-1. ✅ 집계 대상 — 지표마다 다르다

2-4의 쿼리는 `is_representative = TRUE`다. 그런데 **모든 지표가 그래야 하는 것은 아니다.**

| 지표 | 집계 대상 | 근거 |
|---|---|---|
| 선호 장르·국가·배우·감독 | **대표 + `rating IS NOT NULL`** | 같은 영화를 3번 봤다고 그 장르 점수가 3배가 되면 왜곡이다 |
| 평균 별점 · 별점 분포 | **대표 + `rating IS NOT NULL`** | 회차마다 별점이 다를 수 있고, 영화당 하나가 자연스럽다 |
| **캘린더 · 월별 시계열** | **전 회차** + `watch_date IS NOT NULL` | **회차마다 `watch_date`가 다르다.** 대표만 쓰면 재관람이 달력에서 사라진다 |
| **관람 방식 분포** | **전 회차** | 극장에서 보고 나중에 OTT로 재관람하는 것이 이 지표가 잡아야 할 그림이다 |
| **재관람 지표** | **전 회차**, `watch_date` 무관 | 날짜 없는 기록도 회차는 회차다 |
| 총 관람 **편수**(`movieCount`) | **`COUNT(DISTINCT movie_id)`** | ⚠️ 아래 참고. 와이어프레임의 *"135편"* |
| 총 관람 **횟수**(`watchCount`) | 전 회차 `COUNT(*)` | 편수와 다른 지표다 |
| 총 시간 | 전 회차 (RA-3) | |

⚠️ **`movieCount`는 대표 플래그를 세지 않는다 — 이것이 초판에서 바뀐 부분이다.**
4-3의 전제가 *"대표 단일성은 DB로 강제할 수 없어 Service가 조율"*, 동시성은 *"낙관적 수용"*
이라고 명시하고 있고 스키마에도 `UNIQUE`가 없다(`idx_watch_record_representative`는 그냥 `KEY`).
대표 플래그를 세면 **조율이 한 번만 어긋나도 "135편"이 조용히 틀린다.** `COUNT(DISTINCT movie_id)`는
같은 비용에 정의도 말뜻 그대로다.

⚠️ **두 숫자가 다르다는 것을 화면이 설명해야 한다.** *"135편 / 총 152회 관람"* 처럼 둘 다
보여주는 편이 *"편수가 왜 이것밖에 안 되지"* 를 막는다. **`rewatchTop`(아래 4절)이 있으면
화면이 저절로 설명한다** — 이것이 재관람 지표를 넣은 이유 중 하나다.

### RA-2. ✅ 기간 파라미터와 `watch_date IS NULL`

**`watch_record.watch_date`는 nullable이다** — *"오래돼서 기억 안 남"* 을 허용한 설계(2-3).
여기서 **합계가 안 맞는 현상**이 생긴다.

```
누적 통계  = 날짜 없는 기록 포함  → 135편
월별 합    = 날짜 있는 기록만     → 12개월 합이 135보다 작다
```

확정 —

- 기간 집계에서 `watch_date IS NULL`은 **제외**한다. 대신 **`undatedCount`를 `statistics` 응답에
  포함**해 누적과 월별의 합이 다른 이유를 드러낸다. **월별 응답에는 넣지 않는다** — 정의상 항상
  0이라 의미가 없다.
- 파라미터는 **`year`/`month`**. `from`/`to` 임의 구간은 **도입하지 않는다** — `monthlyTrend`가
  전 기간을 내리므로 임의 구간 요구가 여기서 사라졌다(아래 4절).
- **`year`/`month`는 필수이며 서버 기본값을 두지 않는다.** `watch_date`가 `LocalDate`라 시간대
  개념이 약하지만 **기본값을 서버가 정하면 서버 타임존이 개입한다.** 5-0-C가
  `MissingServletRequestParameterException`을 이미 400 `INVALID_INPUT_VALUE`로 매핑해 뒀으므로
  누락 시 응답 포맷도 그대로 맞는다.
- 범위 검증은 **Service 소관**이다 — 5-0-B가 `@RequestParam` 레벨 Bean Validation을 도입하지
  않기로 확정했다. ErrorCode **`INVALID_REPORT_PERIOD`** 신설.
- ⚠️ **미래 월은 거부하지 않는다.** 빈 결과 200으로 응답한다. 초판은 *"미래 월, 1900년 같은 값"*
  을 함께 묶었으나 **둘은 성격이 다르다** — 캘린더는 월 이동 버튼이 달린 화면이라 사용자가 다음
  달을 누르는 것이 정상 동작이고, 거부하면 그때마다 400이 뜬다. `year`에 대해 `1900~2100` 정도의
  sanity 범위만 둔다.

### RA-3. ✅ 총 시간 — 실측으로 닫혔다

와이어프레임이 *"287시간"* 을 보여준다. `movie.runtime` 합산이다.

- **`runtime` 결손은 3 / 4,641 = 0.065%**(2-1절 실측). → **`COALESCE(SUM(runtime), 0)`로 합산하고
  화면 주석도 달지 않는다.** 287시간 기준 오차가 10분 미만이다.
- **재관람은 전 회차를 더한다** — *"본 시간"* 이라는 말뜻 그대로다.
- 편수(고유)와 시간(전 회차)의 기준이 다르므로 **필드명으로 드러낸다**:
  `totalWatchedMinutes`. (초판의 `totalRuntimeMinutes`에서 개명 — *"러닝타임의 합"* 이 아니라
  *"내가 본 시간"* 이 이 값의 의미다.)
- **분 단위로 내리고 시간 변환은 화면에서** 한다.

### RA-4. ✅ 선호 감독 — C안(공동 연출 `1/N` 분배)

**스키마에 실제로 없는 것이라 반드시 부딪힌다.** `movie_genre.weight` · `movie_country.weight` ·
`movie_actor.role_tier`는 있는데 **`movie_director`에는 가중치가 없다**(기획노트 2-5에 명시).
그런데 와이어프레임은 *"선호 감독 TOP 3"* 를 보여준다.

| 안 | 내용 | 판정 |
|---|---|---|
| A | 편수 기준 `COUNT(*)` | ❌ *"많이 본"* 이지 *"선호"* 가 아니다 |
| B | `SUM(rating)` — 별점 합 | △ 장르·배우와 기준이 통일된다 |
| **C** | 공동 연출 `1/N` 분배 후 `SUM(rating × 1/N)` | ✅ **채택** |

**C안을 택하되 근거가 바뀌었다.** 실측 결과 공동 연출은 **305편 / 6.6%**, 영화당 평균 감독
**1.0825명**이라 B안과 결과가 거의 같다. 그래서 *"정확도"* 가 채택 근거가 될 수 없다.

**실제 근거는 일관성이다** — 장르·국가·배우가 전부 *"영화당 기여 총점 고정"* 구조인데 감독만
다르면, **M3-b에서 네 지표를 한 점수로 합칠 때 스케일이 어긋난다.** 지금은 6.6%라 차이가 안
보이지만, 공식을 통일해 두는 비용이 윈도 함수 한 줄이다.

```sql
COUNT(*) OVER (PARTITION BY md.movie_id)   -- 1/N 의 분모. 컬럼 추가 없음 (MySQL 8)
```

#### ⚠️ RA-4의 진짜 쟁점은 공식이 아니라 정렬이었다

와이어프레임의 선호 감독·배우 카드는 **`{count}편`만 표시한다.** score는 화면에 없다. 그런데
score로 정렬하면 *"12편"* 인 2위가 *"15편"* 인 3위보다 위에 온다 — **사용자 눈에는 버그다.**
게다가 월말 리포트의 *"이번 달의 주목"* 은 아예 **"가장 많이 본 감독 · 4편 관람"** 이라
명시적으로 편수 기준이다.

확정 — **두 기준을 공존시키되 필드명으로 의미를 분리한다.**

| 필드 | 정렬 | 화면 문구 |
|---|---|---|
| `topDirectors[]` · `topActors[]` (누적) | **score** | "선호 감독" / "선호 배우" |
| `mostWatchedDirector` (월말) | **count** | "가장 많이 본 감독" |

`score`와 `count`를 **둘 다 내리되**, 누적 통계 카드에서는 **편수를 부제로 쓰지 않는다**(7절).

### RA-5. ✅ 빈 상태와 별점 버킷

- 기록 0건 / 별점 0건 / TOP N에 항목이 N보다 적을 때 → **빈 배열과 0을 정상 응답으로 내린다**
  (404가 아니다). 화면이 `EmptyState`를 그린다.
- 추천의 콜드 스타트(R-3)와는 별개 문제다 — 리포트는 **"아직 기록이 없습니다"가 정답**이고
  폴백 콘텐츠를 끼워 넣을 이유가 없다.

**별점 분포만 예외다 — 정수 1~10 버킷 10개를 `count: 0` 포함해 항상 전부 내린다.**
데이터에 따라 차트 축이 달라지면 **월별 비교가 불가능**하다. 실측에서 5~10만 나온 것이 정확히
이 케이스다.

버킷을 정수 1~10으로 정한 근거는 **프론트 계약이 이미 그렇게 못박혀 있기 때문**이다
(`M2-frontend-spec.md` §7.3) —

```
UI 0.5 ~ 5.0 (0.5 단위)  ⇄  API 1.0 ~ 10.0 (1.0 단위)
표시: apiRating / 2      저장: uiRating * 2
```

⚠️ **그런데 서버 검증이 이 계약을 강제하지 않았다** (v16에서 정정) — `validateRating()`은 `0.0 ~ 10.0` **실수
전체**를 통과시킨다(`jpa-entity-spec.md` 5) WatchRecord). 단계 제약도 하한 `1.0`도 없어
**`7.3`도 `0.0`도 DB에 들어갈 수 있다.** 현재 데이터가 깨끗한 것은 프론트가 유일한 입력
경로이기 때문이지 스키마가 막아서가 아니다.

→ 집계 시 **서버가 정규화한다**: `ROUND(rating)` 후 **1~10으로 클램프**.
→ 별도로 **검증을 §7.3에 맞춘다** — v16에서 `1.0 ~ 10.0`으로 정정했다(9절 ①).
→ ⚠️ **`rating`의 타입도 v16에서 `double` → `DECIMAL(3,1)`로 바뀌었다.** `GROUP BY`에서
  부동소수점이 버킷 키가 되는 문제가 애초에 이 타입에서 나온 것이다(`v16-delta.sql` [1]).

### RA-6. ✅ 공개 범위 — `/api/users/{userId}/report/...`

M2 화면은 **내 리포트만** 본다. 그래서 `/api/users/me/report`로 가고 싶어지는데 —

⚠️ **3군 소셜에서 "팔로잉한 사람의 서재 보기"를 만들면 남의 리포트를 볼 수 있어야 한다**
(기획노트 B-10 대안으로 이미 검토된 방향). 그때 경로를 바꾸면 프론트가 전부 따라 바뀐다.

확정 — **`/api/users/{userId}/report/...`** 로 열어두고 `UserAccessPolicy.validateCanView`를
태운다. 기존 `records`·`collections`·`wishes`가 전부 이 형태라 **일관성도 맞는다.**
`me`는 프론트가 자기 `userId`를 넣으면 된다. `viewerId`는 **nullable**(비로그인 PUBLIC 조회 허용).

⚠️ **초판이 빠뜨린 것 — 화이트리스트 등록이 함께여야 한다.**
5-0-F가 `/api/users/{userId}/…`를 **`permitAll` GET만**으로 규정해 뒀으므로, 등록하지 않으면
기본값 `authenticated`에 걸려 **비로그인 공개 조회가 막힌다.**

```java
GET /api/users/*/report/**      // ⚠️ 반드시 /** 
```

5-0-F가 `GET /api/users/*/records`에서 **이미 한 번 밟은 지뢰**다 — Ant 패턴상 세그먼트 1개만
매칭해 `/records/movies/{movieId}`가 401로 막혔던 건. 처음부터 `/**`로 넣는다.

### RA-7. ✅ 성능과 인덱스 — "확인"이 아니라 "추가"였다

**캐시는 도입하지 않는다.** 판단 근거를 기록해 둔다: 인덱스가 있으면 사용자당 수천 건까지 단일
집계 쿼리로 충분하고, 캐시를 두면 기록 수정 시 무효화 지점이 늘어난다.

**인덱스 2개를 추가한다** (`docs/schema/v16-delta.sql`).

```sql
CREATE INDEX idx_watch_record_user_representative ON watch_record (user_id, is_representative);
CREATE INDEX idx_watch_record_user_watch_date     ON watch_record (user_id, watch_date);
```

> v16에는 **세 번째 인덱스 `idx_watch_record_movie_representative (movie_id, is_representative)`**
> 도 함께 들어갔다. M3-a가 쓰는 것은 아니고 **잔여 #14**(영화 상세의 "우리 평점")용인데,
> `WHERE movie_id = ? AND is_representative = TRUE AND rating IS NOT NULL`로 **M3-a와 정확히
> 같은 형태**이고 `GROUP BY` 대상만 다르다(영화 단위 vs 사용자 단위). 인덱스 한 줄 때문에
> v17 델타를 따로 만들지 않으려고 선반영했다.

실제 스키마(v15)를 대조한 결과 —

- 초판이 기대한 `(user_id, is_representative)`는 **없다.** 있는 것은
  `idx_watch_record_representative (user_id, **movie_id**, is_representative)`로 **`movie_id`가
  중간에 껴서** 대표 필터에 쓸 수 없다(index skip scan 의존).
- **`(user_id, watch_date)`는 아예 없다** — 캘린더·월별·`monthlyTrend`가 매번 사용자의 전 기록을
  훑는다.

**TOP N은 페이징이 아니다** → `PageResponse` 미사용, `size` 파라미터 없음, **서버 상수**로 고정한다
(와이어프레임 기준 장르·국가 5, 배우·감독 3). 5-0-D의 `size` 상한 규약과 충돌하지 않는다.

⚠️ **초판의 *"B-16 작업 때 확인한 인덱스와 대조할 것"* 은 오기였다.** B-16은 `review.rating`
제거 건이고 인덱스 작업이 아니다. 인덱스 관련 선행 이력은 없다.

### 4-2. ★ `monthlyTrend` — 평균을 내리지 않고 시계열을 내린다

*"월 평균 관람 횟수"* 를 단일 숫자로 내리려면 **분모를 정해야 하는데 어느 선택지도 옳지 않다** —

| 분모 | 문제 |
|---|---|
| 기록이 있는 달의 수 | 한 달에 5편 보고 만 사용자의 "월 평균 5.0" |
| 첫 기록 ~ 마지막 기록 | 공백 달이 0으로 들어가 값이 내려감 |
| 가입일 ~ 오늘 / 최근 12개월 | **서버가 "오늘"을 알아야 한다** — RA-2에서 배제한 서버 타임존 개입 |

게다가 화면에 *"월 평균 4.2회"* 만 떠 있으면 사용자는 그 숫자가 뭘 나눈 건지 알 수 없고,
분모를 서버에 박으면 나중에 바꿀 때 클라이언트까지 따라 바뀐다.

**확정 — 첫 기록이 있는 달부터 마지막 기록이 있는 달까지, 공백 달은 0으로 채워 전부 내린다.**

```
monthlyTrend: [ { year, month, watchCount, movieCount, watchedMinutes }, ... ]
```

- **분모 논쟁이 사라진다.** 평균은 이 배열에서 언제든 계산되고, 분모가 *"활동 구간 개월 수"* 로
  데이터에서 자연히 정의된다. 반대 방향(평균 → 시계열)은 복원 불가다.
- **서버 타임존이 개입하지 않는다.** 구간 끝이 "오늘"이 아니라 "사용자의 마지막 기록"이다.
- **차트가 나온다.** `react-native-gifted-charts`를 이미 도입하므로 월별 막대/선 그래프가 그대로
  그려진다. 평균 숫자 하나로는 그릴 것이 없다.
- 비용은 무시할 수준이다 — 10년을 써도 120개 원소. **상한 240개(20년)** 만 이상 데이터 방어용으로 둔다.

⚠️ **`monthlyTrend`의 `watchCount` 합계는 누적 `watchCount`보다 작다.** `watch_date IS NOT NULL`만
담기 때문이며, RA-2가 예상한 현상이다. **숫자 하나일 때는 안 보이던 것이 차트가 생기면 눈에
띄므로**, 화면에 *"날짜 미상 N편 제외"* 를 반드시 표기한다(7절).

⚠️ **`statistics` 응답에 포함하고 별도 엔드포인트로 빼지 않는다.** 갱신 주기가 누적 통계와 같고
(화면 진입 시 1회), 캘린더처럼 월을 넘길 때마다 부르는 성격이 아니다. 분리하면 통계 화면이 두 번
부르게 되어 5절이 C안을 기각한 이유에 그대로 걸린다.

### 4-3. ★ 관람 방식 분포

⚠️ **버킷은 3개가 아니라 4개다.** `watch_type enum('THEATER','OTT','ETC')`가 **nullable**이므로
**`UNSPECIFIED`** 버킷이 필요하다. 빠뜨리면 합계가 전 회차 수와 맞지 않는다 — `undatedCount`와
같은 종류의 구멍이다.

`ott_platform_id`가 있으므로 **플랫폼별 분해**까지 내린다(`ottPlatformDistribution`).
*"OTT 18회"* 아래 *"넷플릭스 12 / 왓챠 4 / 디즈니+ 2"* 가 된다.

⚠️ **응답은 `UNSPECIFIED`를 숨기지 않는다.** 대신 **미지정이 과반이면 차트를 그리지 않고
*"관람 방식을 기록하면 분포를 볼 수 있어요"* 유도 문구를 띄우는 것**을 프론트 규칙으로 둔다
(7절). 차트를 억지로 그려 "미지정"이 화면을 채우는 것보다 입력을 유도하는 쪽이 데이터도 모이고
화면도 정직하다. RA-5 빈 상태 규칙의 변종이다.

✅ **B-13(잔여 #15) 완료** (2026-09-21) — `GET /api/ott-platforms` 신설로 `watch_type=OTT`
저장이 더 이상 막혀 있지 않다. 다만 **완료 이전에 쌓인 과거 기록에는 OTT 시청이 반영돼 있지
않다** — 관람 방식 분포를 볼 때 구간에 따라 OTT 비중이 실제보다 낮게 나올 수 있다는 점은
유의한다(과거 기록은 소급 복구되지 않는다).

### 4-4. ★ 개봉 연대 — 분포가 아니라 성취로 설계한다

10년 단위로 균등하게 자르면 *"2010s 40% / 2020s 45% / 나머지 15%"* 가 되어 **막대 둘이 화면을
먹고 정작 보고 싶은 20세기는 바닥에 눌린다.** 요즘 관람이 21세기 작품에 쏠려 있기 때문이며,
**통계가 특별하지 않은 것이 아니라 버킷이 틀린 것**이다.

설계 의도는 *"20세기 고전이 쌓이면 볼 동기와 성취가 생긴다"* 이고, **그것은 분포가 아니라 성취
지표**다. 그래서 셋으로 나눈다.

| 필드 | 내용 | 근거 |
|---|---|---|
| `releaseDecadeDistribution[]` | **비선형 버킷** — `2020s / 2010s / 2000s / 1990s / 1980s / 1970s / ~1960s / UNKNOWN` | 21세기는 2개로 뭉개고 20세기를 펼친다. *"1970년대 3편"* 이 눈에 보인다 |
| `classicCount` | **2000년 이전 개봉작** 관람 편수 | **성취는 카운터가 만든다.** 분포 차트로는 "늘었다"가 느껴지지 않는다. 나중에 배지·마일스톤으로 확장할 자리다 |
| `oldestWatched` | `{ movieId, title, releaseDate }` | *"가장 오래된 관람작: 1941년"* — 한 줄로 끝나고 가장 강하다 |

⚠️ `movie.release_date`가 **nullable**이므로 `UNKNOWN` 버킷이 필요하다.
⚠️ **"고전"의 경계(2000년)는 상수로 뺀다** — 조정될 가능성이 크다.

### 4-5. ★ 대중 평점과의 차이

`movie.vote_average`가 `decimal(3,1)` **0~10 스케일**이고, **v16에서 `watch_record.rating`도
`DECIMAL(3,1)`이 되어 타입까지 일치한다** — 그 전에는 DECIMAL↔DOUBLE 혼합 연산이라 결과에
부동소수점 오차가 섞였다. 다른 기록 앱이 잘 하지 않는 지표이고 CineMory의 *"분석"* 서사에 가장 잘 맞는다.

⚠️ **모수를 맞춰야 한다** — 비교 대상은 전체 영화의 평점이 아니라 **내가 본 그 영화들의
`vote_average`** 다. 그래서 평균끼리 빼지 않고 **영화별 차이를 먼저 구한다.**

```sql
AVG(wr.rating - m.vote_average)   -- 영화별 차이의 평균
```

수치는 평균끼리 빼는 것과 같지만, 영화별로 구해두면 **가장 크게 갈린 영화**가 공짜로 나온다.

| 필드 | 내용 |
|---|---|
| `ratingBiasAverage` | *"평단보다 평균 +1.2점 후하게"* |
| `mostOverratedByMe` | 차이 최대 — *"나만 좋았던 영화"* |
| `mostUnderratedByMe` | 차이 최소(음수 최대) — *"나만 아쉬웠던 영화"* |

**뒤의 둘이 실제 훅이다.** 평균 하나는 숫자지만 영화 제목이 붙으면 이야기가 된다.

⚠️ 함정 둘 — **`vote_average`가 nullable**이라 제외해야 하고, **`vote_count`가 작은 영화는 대중
평점 자체가 불안정**하다(투표 5명과 5만 명을 같이 취급). `mostOverratedByMe` 같은 **최대값 지표는
투표 수 적은 무명작이 1위로 올라오기 쉽다** → **`vote_count >= 100` 하한을 상수로 둔다.**
평균(`ratingBiasAverage`)에는 하한을 걸지 않는다.

### 4-6. ★ 재관람

| 필드 | 내용 |
|---|---|
| `rewatchCount` | `watchCount − movieCount` — 총 재관람 횟수 |
| `rewatchTop[]` | `{ movieId, title, posterPath, watchCount }`, `HAVING COUNT(*) > 1` |

⚠️ **`watch_date`와 무관하게 센다.** 날짜 없는 기록도 회차는 회차다 — **`monthlyTrend`와 기준이
다른 지점**이라 구현 시 혼동하기 쉽다.

### 4-7. ★ 요일별 분포 — 누적에 둔다

한 달에 10편이면 **요일당 1~2편**이다. 그 분포로 *"주로 토요일에 봅니다"* 를 말하면 **노이즈를
패턴으로 읽는 것**이 되고 다음 달엔 수요일이 1위가 된다.

확정 —

- **`weekdayDistribution[]`은 누적(`statistics`)에 둔다.** 연말 결산에도 포함한다(표본 충분).
- **월말 리포트에는 패턴 주장 없이 한 줄만** — *"이번 달엔 토요일에 가장 많이 봤어요"*.
  차트는 그리지 않는다.

⚠️ **구현 함정** — MySQL `DAYOFWEEK()`는 **1=일요일**, `WEEKDAY()`는 **0=월요일**이다.
어느 쪽을 쓰는지 스펙에 박아두지 않으면 **화면의 요일이 하루씩 밀린다.** → 4-8에서 못박는다.

### 4-8. ★ 기록 습관 — 둘만 채택

후보 다섯 중 둘만 넣는다.

| 후보 | 판정 |
|---|---|
| **활동 기간**(첫 기록일부터) | ✅ 채택. *"CineMory와 함께한 187일"*. `MIN(created_at)` 한 번 |
| **리뷰 작성률**(기록 N편 중 리뷰 M편) | ✅ 채택. 기록 습관을 보여주고 리뷰 작성을 유도한다 |
| 별점 기록률 | ❌ 위와 성격이 겹치고, 사용자에게 보여줄 이유가 약하다 |
| 위시 → 관람 전환율 | ❌ **데이터 구조상 정확히 낼 수 없다**(아래) |
| 연속 기록(streak) | ❌ `watch_date` 결손에 그대로 취약하다. 날짜를 안 적은 날이 끊김으로 잡힌다 |

⚠️ **위시 전환율이 안 되는 이유** — `wish_movie`에 관람 여부 플래그가 없고 `created_at`만 있다.
현재 찜 목록과 `watch_record`의 교집합으로 *"찜한 것 중 본 것"* 은 구할 수 있지만 **보고 나서 찜을
해제한 경우가 통째로 빠진다.** 그게 오히려 정상적인 사용 흐름이라 전환율이 **구조적으로 과소
집계**된다. 제대로 하려면 `wish_movie`에 컬럼을 추가해야 하는데 **리포트 지표 하나 때문에 스키마를
건드릴 값은 아니다.**

채택한 둘은 **별도 카드가 아니라 월말 리포트 *"한 줄 요약"* 문구의 재료**로 쓴다.

**이번 확정으로 프론트가 지켜야 할 규칙 넷**

   바꾸고 정렬 기준도 count로 맞춰야 한다.
3. **관람 방식 분포는 `UNSPECIFIED`가 과반이면 차트 대신 입력 유도 문구**를 띄운다(4-3).
4. **`ratingDistribution`은 10버킷으로 내려온다.** 5구간으로 보여주려면 프론트에서 묶는다 —
   서버가 미리 뭉개면 복원이 불가능하다.

## 9. 이번 확정에서 새로 등록한 항목

① ✅ **`validateRating()`이 프론트 계약(§7.3)과 어긋난다 — v16에서 처리.**
계약은 `1.0 ~ 10.0`, `1.0` 단위인데 검증은 `0.0 ~ 10.0` 실수 전체를 통과시킨다.
프론트가 유일한 입력 경로라 지금은 증상이 없지만, **관리자 도구·배치·API 직접 호출이 생기면
`7.3` 같은 값이 들어와 별점 버킷을 깨뜨린다.** 집계 측 방어(`ROUND` + 클램프)는 RA-5에
넣었으므로 이것은 **입력 측 정정**이다. `jpa-entity-spec.md` 5) WatchRecord 소관.

② **잔여 #14(영화 상세의 평점 표시)와 집계 쿼리가 겹친다.**
#14가 *"`watch_record` 대표 기록 기준 `AVG` 집계 쿼리가 `WatchRecordRepository`에 아직 없다"*
고 적어 뒀는데, **M3-a가 바로 그 쿼리를 만든다.** 4-8 구현 시 #14가 함께 닫히는지 확인할 것
(영화 단위 vs 사용자 단위라 `GROUP BY` 대상이 다르므로 자동으로 닫히지는 않는다).

③ **데모용 기록 시드.** 기획노트 4-M3의 *"데이터 규모"* 항목은 **영화 카탈로그** 이야기였고
(4,641편으로 해결), **사용자 기록 규모는 어디에도 없다.** 기록이 수십 건이면 *"선호 감독
TOP 3"* 가 전부 1편씩이라 순위가 무의미하다. 와이어프레임의 *"135편 / 287시간"* 은 기록이
수백 건일 때의 그림이다. **테스트 시 기록 규모를 늘려 진행한다**(2026-09-20 확인).
